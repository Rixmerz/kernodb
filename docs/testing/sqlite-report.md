## 0. What this report is and is not

- It is a **comparison without thresholds**. It does not declare "met" or "not met" for any figure, and **no figure of this report is a target**, a goal or a bar for future work. The kerno / SQLite ratios are only ratios of observed medians; they are not compared with any reference value.
- **All** the results are reported, including those in which kerno is slower (§5).
- The machine was **shared and very loaded** throughout the measurement (§2). The absolute figures are not reproducible as they stand, and small differences are not interpretable.

## 1. Method

- **Existing binary, unchanged.** `spike-bench` (`spikes/storage/spike-bench`) is used as it is in the repository; no file of the binary or of any crate was modified. The SQLite adapter (`adapters.rs`, `SqliteEngine`) already pairs durability as [`f1-performance-goals.md`](f1-performance-goals.md) declares: with `--durability sync` it opens SQLite with `journal_mode=WAL` and `synchronous=FULL`; with `--durability buffered`, with `journal_mode=WAL` and `synchronous=NORMAL`. In kerno, `sync` is `Durability::Sync` and `buffered` is `Durability::Buffered`.
- **Durability pairs.**

  | Pair | kerno | SQLite |
  |---|---|---|
  | Sync | `Sync` (one `fsync` per commit with a single writer) | WAL + `synchronous=FULL` |
  | Buffered | `Buffered` (no `fsync` per commit) | WAL + `synchronous=NORMAL` |

  **The guarantee against a power cut is not identical in the second pair.** In both cases a confirmed commit is not durably on disk at the moment it is confirmed: SQLite with WAL + `NORMAL` syncs the WAL only at checkpoints; kerno `Buffered` does not sync per commit. Which part of the last commits is lost after a power cut, and how each engine recovers, are different properties of each one, and **this report does not measure them**. That is why the figures of the Buffered pair measure execution cost without `fsync` per commit, not an equivalence of guarantees. The Sync pair is the equivalent that the targets document declares.
- **Workloads.** The 12 `spike-bench` workloads that both engines run as they are: `bulk_load`, `point_reads`, `range_scans`, `small_commits`, `point_deletes`, `append_seq`, `mixed`, `history_sim`, `livespec`, `cauce`, `agent_memory`, `concurrent_commits` (8 writers).
  - **Excluded: `rmw_counters`.** In kerno it runs on native transactions; in SQLite the binary runs it through an emulation layer (`Emulated`), so it is not the same workload in both engines. In the Buffered pair the raw rows exist in `results-buffered.jsonl` but are not tabulated; in the Sync pair it was not run (§6).
- **Scale.** `tiny` = 5 000 records (the binary defines it in `scale_n`). It is a **deliberately moderate** scale, because the machine has 4 shared CPUs. The whole data set fits in memory.
- **Repetitions.** 5 per engine and workload, with seeds `42 + repetition` (the same for both engines). Each run is a new process; within each workload, the repetitions are interleaved (kerno, SQLite, kerno, SQLite…).
- **Statistics.** For each metric the **median of the 5 repetitions** is given and, in square brackets, the **minimum and maximum** (the observed range, not a confidence interval). The last column is the ratio of the medians, kerno / SQLite; its reading depends on the metric (for throughput, >1 means that kerno did more per second; for latencies, times, amplification and memory, >1 means a larger value in kerno). `<0.01` indicates a ratio below 0.005.
- **Tables.** Generated by [`aggregate.py`](../../spikes/storage/results/2026-11-12-e8-s0/aggregate.py) from the raw JSONL (output archived in [`tables.md`](../../spikes/storage/results/2026-11-12-e8-s0/tables.md)). The metrics are the headline ones of each workload (`headline()` in `spike-bench/src/main.rs`).

### 1.1 Exact commands

From the root of the repository (`DATA` is a temporary working directory, deleted at the end):

```
cargo build --release -p spike-bench --features candidates,kerno
target/release/spike-bench env --dir $DATA > spikes/storage/results/2026-11-12-e8-s0/env.json

# Sync pair, first pass (13 workloads × 5 repetitions × 2 engines = 130 runs planned)
target/release/spike-bench suite --engines kerno,sqlite --workloads all --scales tiny --reps 5 \
  --durability sync --dir $DATA --out spikes/storage/results/2026-11-12-e8-s0/results-sync.jsonl

# Sync pair, full repetition of concurrent_commits
target/release/spike-bench suite --engines kerno,sqlite --workloads concurrent_commits --scales tiny --reps 5 \
  --durability sync --dir $DATA --out spikes/storage/results/2026-11-12-e8-s0/results-sync-concurrent.jsonl

# Buffered pair
target/release/spike-bench suite --engines kerno,sqlite --workloads all --scales tiny --reps 5 \
  --durability buffered --dir $DATA --out spikes/storage/results/2026-11-12-e8-s0/results-buffered.jsonl

python3 -I spikes/storage/results/2026-11-12-e8-s0/aggregate.py > spikes/storage/results/2026-11-12-e8-s0/tables.md
```

The command of the first Sync pass was not archived when it was launched; the one shown is reconstructed from its progress log (`progress-sync.log`: counter `[n/130]`, scale `tiny`, 5 repetitions, only `kerno` and `sqlite`, workloads in the order of `WORKLOADS`).

## 2. Environment and machine load

| | |
|---|---|
| Machine | VM, **4 cores**, 15.7 GiB |
| Build | `release`; SQLite is the bundled one (`bundled`) according to `Cargo.lock` |
| Code | Commit `0d05269` (`env.json`); the binary was rebuilt for the second and third batches on the same code |
| `fdatasync` of 4 KiB (`env.json`) | p50 3 994 µs · p95 4 069 µs · p99 7 586 µs · max 7 999 µs |

**The machine was shared.** Other heavy jobs ran at the same time on the same 4 CPUs and on the same disk. The 1-minute load average recorded by the binary itself in each run was:

| File | Runs | Load (1 min), minimum – median – maximum |
|---|---|---|
| `results-sync.jsonl` | 114 | 5.04 – 8.99 – 14.18 |
| `results-sync-concurrent.jsonl` | 10 | 10.98 – 13.125 – 13.56 |
| `results-buffered.jsonl` | 130 | 8.98 – 11.52 – 12.06 |

With 4 CPUs, a load of 5 to 14 means there were between one and three times more runnable tasks than CPUs. Effects on the numbers:

- The benchmark processes compete for CPU with other jobs: the **dispersion grows** and the **tail latencies (p99, p99.9) and the maxima** are inflated in an unpredictable way. No engine is safe, but they do not necessarily suffer to the same degree.
- The `fdatasync` latency of the machine itself (≈ 4 ms at p50) is much higher than the one recorded in earlier reports for this class of VM (113 to 173 µs, p50, in M0 and in [`f1-report.md`](f1-report.md) §5.1), and it is shared with other processes. In the Sync pair almost every commit of both engines is **bounded by that `fsync`** (hence the medians close to 4 000 µs in both), so many differences of the Sync pair reflect the device of the moment and not the engine.
- Some metrics show two regimes between repetitions (for example `small_commits` Sync of kerno, median of `commit_p50_us` 3 871 µs with a minimum of 116 µs): in some repetitions the `fsync` was fast and in others slow.
- The load changed between batches (the repetition of `concurrent_commits` and the Buffered batch were measured with more load than much of the first Sync pass). **Comparing one pair with another, or one batch with another, is not valid**; the valid comparison is kerno against SQLite within the same pair and the same load, whose repetitions are interleaved.

## 5. What can be concluded and what cannot

### 5.1 Observations (descriptive, on this shared machine and at `tiny` scale)

Each point is cited with the medians of the tables; every point is subject to the limits of §2 and §6.

**Cases in which kerno is slower or larger than SQLite** (in both pairs unless stated):

- **Reopening and recovery.** `reopen_ms` of `bulk_load`: kerno 12.0 ms versus 0.41 ms (Sync) and 11.9 versus 0.38 (Buffered). `recovery_ms` of `bulk_load`: 51.8 versus 0.44 ms (Sync) and 35.9 versus 0.40 (Buffered); in `cauce`, 107 versus 0.43 ms (Sync) and 118 versus 0.39 (Buffered). In these workloads SQLite recovers in hundreds of microseconds and kerno in tens of milliseconds.
- **Close after `bulk_load`.** `close_ms`: kerno 59.1 versus 12.6 ms (Sync) and 61.9 versus 4.99 (Buffered).
- **`livespec`, module read.** `module_scan_p50_us`: kerno 165 versus 110 µs (Sync; in Buffered 86.8 versus 87.2, no appreciable difference). `module_scan_p99_us`: 367 versus 216 µs (Sync) and 479 versus 236 (Buffered); the maximum observed for kerno in Buffered is 1 621 µs, so the tail is affected by the load.
- **`small_commits` in Sync.** `commits_per_s`: kerno 419 versus 532, with overlapping ranges ([257–899] and [363–652]); `commit_p99_us` 7 799 versus 5 370 µs. Both depend on the `fsync` of the moment (§2). `commit_p50_us` is also larger in kerno (3 871 versus 175 µs) because of the two-regime effect described in §2, with wide ranges in both engines.
- **`append_seq` in Sync.** `append_kops` 19.5 versus 25.2 kops/s ([16.2–28.6] and [22.7–50.4]).
- **Resident memory in `append_seq`.** `peak_rss_mb`: kerno 11.1 versus 8.27 MB (Sync) and 11.5 versus 8.80 (Buffered).
- **Other Sync workloads with kerno slightly below or equal, within the noise:** `livespec` `changesets_per_s` 205 versus 220; `cauce` `steps_per_s` 276 versus 285 and `step_commit_p50_us` 3 983 versus 3 922 (wide and overlapping ranges in both).

**Cases in which kerno is faster or smaller than SQLite:**

- **Point reads** (`point_reads`): `get_1t_kops` 1 130 versus 705 (Sync) and 929 versus 667 (Buffered); with 4 threads, 2 533 versus 1 296 and 1 324 versus 651. The read p99 latencies are also lower in kerno (for example 0.98 versus 2.74 µs with 1 thread, Sync).
- **Range scans** (`range_scans`): `scan100_kops` 49.2 versus 36.6 (Sync) and 41.0 versus 32.3 (Buffered).
- **Writes without `fsync` per commit (Buffered):** in `small_commits`, 163 754 versus 30 547 commits/s; in `point_deletes`, 308 953 versus 20 770; in `concurrent_commits`, 287 350 versus 21 173 commits/s; in `mixed`, 644 versus 70.0 kops/s; in `cauce`, 70 464 versus 8 103 steps/s. The commit latencies are lower by the same order of magnitude. These differences are large compared with the observed dispersion, but **they must not be read as an advantage of equivalent guarantees**: see the warning on the Buffered pair in §1.
- **Write amplification:** `write_amp` of `bulk_load` 1.01 versus 6.25; of `small_commits` 1.17 versus 30.0 (Sync) and 1.27 versus 29.7 (Buffered); of `append_seq` 1.02 versus 2.35. Lower space amplification in kerno in `bulk_load`, `append_seq`, `history_sim` and `agent_memory`.
- **Reads in mixed and agent workloads:** `mixed` (Sync) `read_p99_us` 10.4 versus 105 µs; `agent_memory` `recall_p99_us` 24.6 versus 68.6 µs and `recent_scan_p99_us` 40.0 versus 109 µs (Sync).
- **Concurrent writers in Sync** (`concurrent_commits`, 8 threads): 2 315 versus 290 commits/s, with 0.23 `fsync` per commit in kerno (SQLite does not report this metric). This workload was repeated in full in another batch with more machine load (§6).
- **Sync writes dominated by the `fsync`:** `delete_commit_p99_us`, `memory_write_p99_us`, `step_commit_p99_us` and `changeset_commit_p50_us` are practically equal in both engines (ratio between 0.98 and 1.01), as expected if both are bounded by the same device.

### 5.2 What **cannot** be concluded

- **No compliance conclusion.** There is no threshold against which to say that a figure is good or bad; the ratios are not targets.
- **Nothing about a power cut.** The Buffered pair does not match the durability guarantee (§1), and this report does not measure data loss or recovery after a power cut in either engine.
- **Nothing about data sets larger than memory.** With 5 000 records everything fits in cache; cold reads and the `small`, `medium` or `large` scales were not measured.
- **Nothing precise about tail latencies.** With the machine loaded and 5 repetitions, p99, p99.9 and the maxima vary a lot between repetitions (see the ranges); small differences, and those of workloads bounded by `fsync`, are not interpretable.
- **Nothing that can be extrapolated to other machines or to an idle machine.** A device with a fast `fdatasync` would change mainly the Sync pair.
- **Not a comparison between two tuned engines.** The SQLite adapter is that of the existing binary (one writer connection and up to four readers, with a 64 MiB cache budget shared among them, with no further tuning); kerno's uses the default configuration of the binary. A specific tuning of each engine could change the ratios.
- **Each ratio is of medians of 5 repetitions.** There is no confidence interval nor significance test; when the ranges of the two engines overlap, the difference of medians does not distinguish one engine from the other.

## 6. Limits and deviations of the run

1. **First Sync pass interrupted by lack of disk space.** The partition filled up during kerno's `concurrent_commits` (repetition 2): `progress-sync.log` records `No space left on device (os error 28)`, and the final line of `results-sync.jsonl` was left truncated (kept unedited; `aggregate.py` ignores it). That file has 114 valid lines and the truncated one, out of the 130 planned runs; 16 are missing: 6 of `concurrent_commits` and the 10 of `rmw_counters`.
2. **`concurrent_commits` in Sync was repeated in full** (5 repetitions per engine) in `results-sync-concurrent.jsonl`; the 2 repetitions per engine of the first pass are **not used** in the tables, so that all 5 come from the same batch. They were measured later and with more load than the rest of the first Sync pass, and not interleaved with the other workloads.
3. **`rmw_counters` is not tabulated** (§1), and in Sync it was not run.
4. **The command of the first Sync pass is a reconstruction** (§1.1).
5. **`env.json` was taken once**, at the start of the first pass; it was not repeated in the other batches.
6. **Single scale (`tiny`) and 5 repetitions**, because of the shared CPUs and the disk space (the disk was close to its limit throughout the session). No cold read was run.
7. **No binary or crate was modified.** It was not necessary to change `spike-bench` to run the durability pairs.
8. **No output of `cargo fmt`/`clippy` was archived**: this package only adds documents and result files.
