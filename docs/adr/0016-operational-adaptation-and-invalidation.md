## Context

The specification proposes that the engine learn to execute frequent queries better (Stage 6) without changing their meaning, and that every adaptation can be inspected, measured, disabled and reverted. It is necessary to decide what the engine may learn, where that state lives, when it is invalidated, and how it is proven that it does not alter results.

## Options considered

1. **No adaptation**: a deterministic planner based only on statistics. Mandatory baseline in any case.
2. **Adaptation limited to one reversible optimization** (proposal for Stage 6): a single mechanism, for example a plan reusable by fingerprint or a result cache invalidated by commit sequence, with complete metadata (spec §9) and comparison against the disabled mode.
3. **General adaptation** (learned weights for several paths, automatic indexes). Larger error surface; the specification also prohibits autonomous schema changes without an explicit policy.

## Decision criteria

1. Equivalence with the reference path (I-32) in the differential test, with the optimization enabled, disabled and invalidated midway through execution.
2. Net improvement measured against the disabled mode, with thresholds set before measuring (ADR-0012), including maintenance, memory and storage cost.
3. Invalidation proven for each declared dependency (I-35).
4. Global and per-query disabling (I-36) and deletion with no effect on the data (I-34).

## Evidence

Stage 5 left the deterministic planner, the reference path and the planner/reference differential test in CI (I-32 verified for indexes, [stage5-closure.md](../architecture/stage5-closure.md)), and `ExecutionObservation` with levels (E5-03, E5-04). There is still no evidence for any learned optimization: the Stage 6 benchmark will provide it.

## Guarantees (conditions of the owner, 2026-11-07)

A learned optimization can only be enabled if it meets all these guarantees; each one has its test in Stage 6.

| # | Guarantee | Rule | Test |
|---|---|---|---|
| G1 | Adaptation never compromises correctness | The optimized path returns the same multiset (and the same order, if the query fixes it) as the reference path over the same snapshot | I-32: differential test with the optimization enabled, disabled and invalidated midway through execution |
| G2 | The reference path always exists | It is kept, compiled and tested in CI even when not used; on any unmet precondition, unknown dependency, error, discrepancy or doubt, the planner executes the reference path (or another valid plan without learned state) | I-33: injection of false preconditions, invalidations and failures of the learned state |
| G3 | Observations are not authority | `ExecutionObservation` only proposes candidates and estimates costs; it never proves that a path is valid nor replaces a check. Validity comes from the preconditions checked at each use and from the differential test, not from how many times it worked. Historical observations may be used as statistical signals to propose optimizations, but never as evidence that the current preconditions are still valid. An old observation does not authorize executing a plan: before using it the current preconditions must be verified and the equivalence guarantees with the reference path maintained. | Test with falsified or corrupt observations: the result still meets I-32; a plan proposed by observations prior to a change of dependency is not executed without re-verifying its preconditions |
| G4 | Invalidation is explicit | Each optimization declares its dependencies with a version number; they are checked **before each use**, and one that does not match invalidates the optimization. What the code declares today is `SchemaVersion`, `PlannerVersion`, `IndexState`, `IndexWatermark` and `CommitSeq` (`Dependencies` in `crates/kerno-units/src/cache.rs`); there are no versioned dependencies apart from statistics, index definition or preconditions (see "Review of 2026-11-13", point 3). A result cache is tied to the commit sequence of its snapshot and serves no other sequence; the exception "unless it is proven that the data read did not change" is removed until a later ADR defines that proof | I-35: one case per declared dependency |
| G5 | Learning does not skip validations | A learned path goes through the same checks as the planned one: filter, active state and order (`check_units` / `check_relations`, `planner.rs`) over the rows that will be returned; no cache returns rows without those checks nor avoids the engine's invariants. A cache hit **re-reads nothing**: the rows come from the cache's memory and the check is on them, not a verified read from the store (see "Review of 2026-11-13", point 2) | Mutations that remove a check on the learned path die in the suite |
| G6 | Adaptation is reversible | Disabling it (globally or per query), invalidating it or deleting its state does not change confirmed data, revisions, relations, transactional indexes or the commit sequence, and the query semantics stay the same | I-34, I-36: full suite with the adaptation disabled; logical state and `commit_seq` equal before and after |
| G7 | Traceability | Every decision about an optimization (creation with its evidence, activation, use, fallback with its cause, invalidation with the dependency that changed, disabling, deletion) is recorded in the cache's transition log with the version of the optimization and of the planner; that log is in memory and bounded, not a persisted audit log (see "Review of 2026-11-13", point 4). That a read used the cache is stated by the `path` and `source` of `QueryOutcome`, and that a read would consult or use it is stated by the plan explanation (`Plan::cache()`, "Review of 2026-11-13", point 4). The log follows the privacy rules of ADR-0015 (no literals or content) | Test that walks each transition and finds its record; sentinels (I-37) |

## Decision

Accepted by the owner on 2026-11-09: option 2, subject to guarantees G1–G7. The learned state is derived data: it is stored separately from user data, does not take part in user transactions, and is rebuilt from observations or discarded. Invalidation by version number: each optimization records the versions of schema, planner and index state it depends on, and these are checked before each use (statistics and data read are covered by the exact match of the commit sequence, not by a version of their own); a result cache also records the commit sequence of its snapshot and does not serve reads from another sequence (G4).

## Review of 2026-11-13

On 2026-11-13 the owner, by express delegation, confirmed this ADR (D16) after reviewing G1 to G7 against the code. **G2, G3 and G6 are confirmed as written.** Where the text promised more than the code does, the text was corrected and the difference remains as open work; no promise is silently dropped.

1. **G1 and G5, learned state only from the planner (code change).** `ResultCache::create`, `ResultCache::activate`, `CacheEntry::new` and `Dependencies::current` were public and re-exported: a caller could plant rows that were then served as the answer. Now the planner uses `pub(crate)` versions (`store`, `arm`, `build`, `in_force`), and the four public ones exist only with the `test-support` feature of `kerno-units` and in the crate's unit tests, as in decision D23 ([stage9-engine-uses.md](../architecture/stage9-engine-uses.md)). Test: four doctests of `ResultCache` (`cache.rs`), one per function, which without the feature must **fail to compile** (`compile_fail,E0599`) and with it compile. Mutation (restore the public path, one at a time, in a copy): removing the `cfg` at `cache.rs:854` (`create`), `:860` (`activate`), `:305` (`CacheEntry::new`) or `:166` (`Dependencies::current`) makes the corresponding doctest fail with `... compile fail ... FAILED` and "Test compiled successfully, but it's marked `compile_fail`". The `cache`, `cache_planner` and `cache_reversibility` tests now require `test-support` in `Cargo.toml`.
2. **G5, what `check_units` really checks.** It checks, over the rows that will be returned, that each unit is active, that it meets the filter, and that the order is strictly ascending by identifier as in the reference path (`check_relations`, the analogue for relations). On a hit there is **no verified read**: the rows come from the cache's memory, and what guarantees that they are the ones of the snapshot is the exact match of dependencies (point 3). If the check fails, the planner abandons the cache, records the `fallback` and answers through the reference path.
3. **G4, dependencies actually declared.** The code declares `SchemaVersion`, `PlannerVersion`, `IndexState`, `IndexWatermark` and `CommitSeq`. **There are no** versioned dependencies for statistics, for index definition or for preconditions. Statistics and data read are covered only because the entry is served only when the commit sequence is **exactly equal** to that of the snapshot that created it. That condition is stronger than a version of statistics or of data: any commit, whether or not it is relevant to the query, invalidates the entry, so no statistic or datum can have changed without the entry ceasing to be served. The cost is that it over-invalidates (false cache misses), never under-invalidates; the reopening condition of this ADR covers that cost. A different `IndexState` or index watermark also invalidates, even if the sequence does not change (the index rebuild).
4. **G7, known limits and open work.**
   - The transition log is **in memory and bounded** (1024 records or one hour by default, `CacheConfig`) and is lost on close; it is not a persisted audit log, consistent with decision D8 of the minutes of Stage 9. Declared limit.
   - ~~`ResultCache::set_key` deletes entries, log and counters without leaving a transition record~~ **Done in P3** (open work 3, below): `set_key` now leaves a `KeyReplaced { entries }` record in the new log (`cache.rs`, `set_key`); `clear` still leaves `Cleared`.
   - **Open work 1, done in P3:** the plan explanation says whether the result cache was consulted and whether it answers with learned state. `Plan::cache()` returns a `CacheView` (`plan.rs`): `Off`, `Miss(cause)`, `Invalidated(dependency)`, `Discrepancy(violation)` or `Hit { evidence, cost_ns }`, plus `NotApplicable` (associative queries and plans built with `Plan::new`). `explain_filter` and `explain_relations` compute it with `ResultCache::peek`, which leaves no record, counts nothing and removes nothing, and with the same row checks as the use (`check_units` / `check_relations`): an entry that the use would reject is announced as `Discrepancy`, not as `Hit`. `Plan::answering_path()` gives `ResultCache` if the learned state answers. It is consistent with `QueryOutcome` because `learned_state_used()` is true if and only if the next read on the same snapshot returns `path == ResultCache` with `source == Cache` (tests in both engines). The cache still is not a candidate of `candidates()`: it is chosen by exact dependency match, not by cost.
   - **Open work 2, done in P3** (H-3 of Stage 6): the creation evidence is no longer the constant. It is what the planner's observer (`Observer`) had for that query shape when the entry was created: executions with an `Ok` result retained with the same fingerprint, **plus the execution that concludes** (which `query` records right after), and the window, from the oldest until now, on the observer's clock (`Observer::evidence_of`, `observation.rs`). The entry also carries the measured cost, in nanoseconds as the observer measures it (`duration_ns`), of the execution it replaces: the one that has just given the answer, through the planned path or the reference (`CacheEntry::cost_ns`, `Transition::Created { evidence, cost_ns }`, and `CacheView::Hit`). `CacheEntry::build` rejects an entry without observations (`NoEvidence`) or without cost (`NoCost`): such an entry is not created and therefore cannot be activated. **Consequence that changes behaviour:** the observer is off by default and, below `Fingerprint`, does not keep per-execution records, so there is no evidence; with the cache on and the observer below that level the planner **creates no entries** and no read is served from the cache. To use the cache the observer must be raised to `Fingerprint` or higher. The evidence serves only to propose the entry; it does not decide whether it is served (G3): the lookup does not read the observer, and emptying the observer does not remove entries. Limits: a busy observer (the planner does not wait for its lock) or one without a key gives "no evidence" and the entry is not created on that read; the window uses the observer's clock, not the cache's.
   - **Open work 3, done in P3:** the log leaves a footprint of `set_key` (first point of this list).
5. **ADR-0018, derivatives and suppression.** ADR-0018 counts caches and learned optimizations as derived artifacts, with a descriptor and with invalidation when a source is suppressed (criterion 3, ADR-0009). This ADR did not say so. Reviewed against the code: **a forget or suppression cannot leave a cache response servable**, because deleting a unit, and the purge of a retention, are commits (they change the commit sequence) and a hit requires the exact sequence. Test: `crates/kerno-units/tests/cache_forget.rs`, in `emulated_log` and `kerno_db`: the response is cached and served (the test is not empty), the unit is deleted or the retention runs, and the next read of a new snapshot does not come from the cache and does not return the forgotten unit. A snapshot taken before the forget still sees its own state, like any snapshot. Relation between the two ADRs: ADR-0016 governs cache invalidation by commit sequence and does not use the derivatives registry of ADR-0018; the cache has no descriptor or sources per unit, and does not need them for this guarantee because its invalidation is coarser (every commit). If a future cache served data from another sequence (the exception that G4 removed), it would have to record its sources as ADR-0018 asks. The limit of ADR-0009 still applies: nothing promises physical deletion, and cached rows live only in memory until close.
6. **Discrepancy.** The actual behaviour is: the cause (`Discrepancy`) is recorded in the cache's transition log, the entry is deleted (`DeleteReason::Discrepancy`), and the response is that of the reference path, which may be saved again as a new entry. The optimization is not disabled for that query. See [adaptive-execution.md](../architecture/adaptive-execution.md) §2 and §4.

## Consequences

- The planner needs monotonic versions for schema, indexes and statistics since Stage 5.
- Reads do not mutate user data (spec §2); recording observations or updating statistics from a read writes only to the derived store and never blocks the writer.
- Equivalence requires that the reference path be kept and tested in CI even though it is not used in production.

## Conditions for reopening

Evidence that a second optimization provides more utility than the chosen one, or evidence that invalidation by version produces so many cache misses that it is not useful.
