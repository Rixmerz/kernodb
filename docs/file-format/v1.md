## 0. Alcance y notación

Este documento especifica **byte a byte** los tres tipos de archivo del motor (`MANIFEST`, `NNNNNN.wal`, `NNNNNN.sst`), las reglas de validación que aplica cualquier lector, las reglas de recuperación que forman parte del formato y las invariantes que cualquier escritor debe respetar. Lo que no está aquí (política de compactación, tamaños objetivo, hilos) no forma parte del formato y puede cambiar sin migración.

- Cada regla tiene un identificador (`HDR-n`, `VAR-n`, `WAL-n`, `SST-n`, `MAN-n`, `REC-n`, `W-n`, `SEM-n`, `VEC-n`). Los mensajes de error y los `Issue` de `verify()` citan el identificador; nunca incluyen bytes de claves ni de valores (amenaza T-08).
- Clases de resultado: **`Corruption`** (daño o archivo fabricado), **`Incompatible`** (versión o característica desconocida o no soportada; no es daño), **`InvalidArgument`** (el directorio no es una base de Kerno, o no existe), **solo lectura** (la base se abre pero rechaza escrituras con `ReadOnly`).
- «Huérfano» significa un archivo canónico que el estado recuperado no necesita: se borra en lectura-escritura y solo se informa en solo lectura y en `verify()`.

## 1. Convenciones

### 1.1 Enteros, varints y cadenas

- Todos los enteros de ancho fijo son **little-endian**.
- **VAR-1.** `varint` es LEB128 sin signo de como máximo 10 bytes; el décimo byte debe ser `0x00` o `0x01`. Un varint cortado por el final de la estructura que lo contiene infringe la regla de esa estructura, como cualquier campo truncado (§13.1).
- **VAR-2.** La codificación debe ser **mínima**: un último byte `0x00` precedido de un byte con bit de continuación es `Corruption` (el valor 0 se codifica como un único `0x00`). Así, decodificar y volver a codificar reproduce los mismos bytes.
- **VAR-3.** `bytes(x)` es `varint(len) ‖ x`; `len` se valida contra el límite del contexto (§1.4) y contra los bytes restantes **antes** de reservar memoria. Lo mismo vale para toda longitud leída del disco (la `len` de un TLV, `key_len` y `value_len` de una entrada de un bloque de datos): si supera el límite del contexto o los bytes restantes de la estructura que la contiene, la regla es VAR-3.

### 1.2 Checksums

- Algoritmo: **CRC-32C** (Castagnoli, polinomio reflejado `0x82F63B78`, valor inicial `0xFFFFFFFF`, xor final `0xFFFFFFFF`, sin máscara), el de la crate `crc32c`. Valor de control: `crc32c("123456789") = 0xE3069283`.
- **CRC con contexto.** `crc(ctx; datos)` = `crc32c(ctx ‖ datos)`, donde `ctx` no se almacena: lo aporta el lector. Así un bloque copiado de otro archivo u otro desplazamiento no verifica.

| Estructura | `ctx` |
|---|---|
| Cabecera común | ninguno (incluye ya `file_number` y `db_id`) |
| Trama del WAL | `file_number u64` (el número del nombre del archivo) |
| Bloque de SST | `file_number u64 ‖ block_offset u64` (desplazamiento del primer byte del bloque) |
| Pie de SST | `file_number u64` |
| Registro del MANIFEST | `generation u64` (el `file_number` de la cabecera del MANIFEST) |

### 1.3 TLV

`TLV = tag varint ‖ len varint ‖ value[len]`. Las reglas de orden, repetición y etiquetas desconocidas dependen de la estructura (§7.6, §8.3). Un `value` de tipo `varint` debe ocupar exactamente `len` bytes; uno de tipo `u8` tiene `len = 1`. Un `value` que no cumple esto (un varint cortado por `len` o seguido de más bytes, un `u8` con `len ≠ 1`) infringe la regla de la estructura; VAR-1 y VAR-2 dentro del valor se informan como tales.

### 1.4 Límites

Los **límites de formato** los aplica cualquier lector (`Corruption` si se superan). Los **límites de API** de la Fase 1 son más estrictos y los aplica el escritor con `InvalidArgument` antes de escribir nada; subir un límite de API dentro del límite de formato no es un cambio de formato.

| Elemento | Límite de formato | Límite de API (Fase 1) |
|---|---|---|
| Clave de usuario, extremos de un rango | 16 KiB | 512 B (`MAX_KEY_LEN`) |
| Valor | 64 MiB | 1 MiB (`MAX_VALUE_LEN`) |
| Operaciones por commit | 2^24 | 2^20 (`Limits::max_batch_ops`) |
| Bytes codificados por commit | carga de trama ≤ 2^30 | 64 MiB (`Limits::max_batch_bytes`) |
| Commits por trama del WAL | 1..=65 536 | grupo ≤ 1 024 (`GroupCommitConfig`) |
| Carga de una trama del WAL | 1..=2^30 bytes | — |
| Carga de un bloque de datos de SST | ≤ 80 MiB | objetivo 4 KiB |
| Carga de un bloque meta de SST, de un registro de MANIFEST | ≤ 256 MiB | — |
| `header_len` | 96..=4096, múltiplo de 8 | 96 |
| Número de archivo | 1..=2^48−1 | — |
| Secuencia de commit | 1..=2^63−1 (0 = base vacía) | agotada ⇒ `InvalidArgument` |
| `edit_seq` de un registro del MANIFEST | 1..=2^63−1 | — |
| Niveles (`num_levels`) | v1 acepta exactamente 7 | 7 |
| Archivos por nivel | ≤ 2^20 | — |
| Filtro bloom: `k`, `nbits` | `k` 1..=30; `nbits` ≥ 64, múltiplo de 8, ≤ 2^32−8 | `k` = 7, 10 bits por clave |

## 2. Directorio

| Nombre | Cabecera | Reglas |
|---|---|---|
| `LOCK` | ninguna (exento: no contiene estado) | 0 bytes; nunca se borra; se toma (exclusivo) antes de cualquier mutación. Es el único archivo que una apertura de solo lectura, `verify()` o `inspect()` pueden crear. |
| `MANIFEST` | `KRNO_MAN` | Nombre fijo. No existe archivo `CURRENT`: cada *checkpoint* reemplaza `MANIFEST` por rename atómico (§8.9). |
| `MANIFEST.tmp` | `KRNO_MAN` | Solo existe durante un checkpoint. Uno viejo se ignora en solo lectura y se borra en lectura-escritura. |
| `NNNNNN.wal` | `KRNO_WAL` | Journal de commits (§6). |
| `WAL.spare` | — | WAL de reserva: ceros, sin cabecera de formato (§6.5). Lo crea el escritor y solo se renombra a `NNNNNN.wal` cuando está completo y duradero; uno que queda tras una caída puede estar a medias y no se usa. Se ignora en solo lectura y se borra en lectura-escritura, al abrir y al cerrar. |
| `NNNNNN.sst` | `KRNO_SST` | Tabla ordenada inmutable (§7). |
| `CURRENT`, `OPTIONS`, `IDENTITY` | — | Nombres **reservados**; v1 no los escribe. Si aparecen, se tratan como desconocidos. |
| Cualquier otro | — | Desconocido: se ignora y nunca se borra; `verify()` lo informa. |

- **DIR-1.** Un nombre es canónico si es `{n:06}.wal` o `{n:06}.sst` con `format!("{n:06}") == raíz` y `1 ≤ n ≤ 2^48−1`. `1.wal`, `0000001.wal` o un número mayor que 2^48−1 son «desconocidos». Los números de WAL y SST salen de un único contador (`next_file`) y nunca se reutilizan.
- **DIR-2 (creación).** Solo se crea una base si el directorio no existe o contiene únicamente `LOCK`, `MANIFEST.tmp` y/o `WAL.spare`. Un directorio con cualquier otro archivo y sin `MANIFEST` no se toca: `InvalidArgument("not a Kerno database")` (cubre `data.kbt` del prototipo B+ tree y `log` del motor de referencia).
- **DIR-3 (protocolo de creación).**
  1. Si el directorio no existe: `create_dir_all` y `sync_dir(padre)`. Es el único caso en que se sincroniza el padre.
  2. `lock(LOCK)`.
  3. Escribir `MANIFEST.tmp` (cabecera con `generation` 1 y `first_edit_seq` 1) con un único registro `SNAPSHOT{edit_seq 1, CLEAN, last_seq 0, next_file 1, log_number 1, prev_generation 0, sin archivos}` → `sync_data` → `rename` a `MANIFEST` → `sync_dir`.
  4. Arranque de sesión normal (§9.4).

  Una caída durante la creación deja como mucho `LOCK` y `MANIFEST.tmp`, que DIR-2 vuelve a tratar como «crear».

## 3. Cabecera común (96 bytes, desplazamiento 0)

Todo `MANIFEST`, WAL y SST empieza con esta cabecera; también los archivos de solo anexado (ADR-0003 §1 permite la cabecera al final, pero un log no puede terminar en una cabecera mientras se escribe).

| Despl. | Tamaño | Campo | v1 |
|---|---|---|---|
| 0 | 8 | `magic` | `KRNO_MAN`, `KRNO_WAL` o `KRNO_SST` (`KRNO_EXP` reservado para la exportación lógica de la Fase 4) |
| 8 | 4 | `format_version` u32 | 1 |
| 12 | 4 | `header_len` u32 | 96 |
| 16 | 8 | `compat` u64 | §4 |
| 24 | 8 | `ro_compat` u64 | §4 |
| 32 | 8 | `incompat` u64 | §4 |
| 40 | 16 | `db_id` | aleatorio al crear la base (inyectable en pruebas); igual en todos los archivos de la base |
| 56 | 8 | `file_number` u64 | WAL y SST: el número del nombre. MANIFEST: `generation` (≥ 1, +1 por checkpoint) |
| 64 | 24 | campos por tipo | ver abajo |
| 88 | 4 | `reserved` u32 | 0 |
| 92 | 4 | `header_crc` u32 | `crc32c(bytes[0 .. header_len−4])` |

Campos por tipo (bytes 64..88; todo byte no listado vale 0):

| Tipo | Campos |
|---|---|
| MANIFEST | `first_edit_seq u64 @64`: `edit_seq` del registro 0 de este archivo |
| WAL | `base_seq u64 @64`: secuencia que debe llevar el primer commit del archivo (= última secuencia anterior + 1) |
| SST | `block_size u32 @64`: tamaño objetivo de bloque de datos, informativo (512..=1 MiB; v1 escribe 4096) |

**Regla permanente (todas las versiones futuras):** `magic` @0, `format_version` @8 y `header_len` @12 no cambian de sitio, y el CRC de la cabecera ocupa siempre los últimos 4 bytes de `header_len`. Una versión futura puede alargar la cabecera; un lector v1 la valida con su CRC y la rechaza por versión (HDR-4) antes de interpretar nada más.

**Orden de validación** (idéntico para los tres tipos; se ejecuta antes de cualquier escritura):

- **HDR-1.** Archivo de menos de 96 bytes: `Corruption`, salvo los WAL sin tramas que REC-7 y REC-10c permiten (un WAL recién creado cuya cabecera aún no era duradera).
- **HDR-2.** `magic`: el del tipo esperado ⇒ continuar. Un *magic* del prototipo M0 (`KRNOMAN1`, `KRNOSST1`, `KRNOLOGC`) ⇒ `Incompatible("M0 prototype format")`. Cualquier otro ⇒ `Corruption`.
- **HDR-3.** `header_len` fuera de 96..=4096, no múltiplo de 8, mayor que el archivo, o CRC incorrecto ⇒ `Corruption`. El CRC se comprueba **antes** que la versión, para que un daño aleatorio nunca se presente como `Incompatible`.
- **HDR-4.** `format_version` = 0 ⇒ `Corruption`; > 1 ⇒ `Incompatible`.
- **HDR-5.** `header_len` ≠ 96 con `format_version` = 1 ⇒ `Corruption`.
- **HDR-6.** `incompat` con algún bit desconocido, o con `AEAD` ⇒ `Incompatible`.
- **HDR-7.** `ro_compat` con algún bit desconocido ⇒ la base entera se abre en solo lectura.
- **HDR-8.** Bits `compat` desconocidos ⇒ se ignoran; un archivo reescrito (checkpoint, compactación) no los conserva (un escritor solo pone bits que implementa).
- **HDR-9.** `reserved` @88 o los bytes de campos por tipo no usados ≠ 0, o `block_size` de una SST fuera de 512..=1 MiB ⇒ `Corruption`.
- **HDR-10.** WAL y SST: `db_id` ≠ el del `MANIFEST`, o `file_number` ≠ el número del nombre ⇒ `Corruption("file belongs to another database or was renamed")`.

## 4. Bits de características

### 4.1 Registro v1

| Palabra | Bit | Nombre | Estado en v1 |
|---|---|---|---|
| `incompat` | 0 | `AEAD`: bloques, registros y tramas sellados; las ranuras de §5 están en uso | Definido y **no soportado** en la Fase 1 ⇒ `Incompatible("encryption not supported")` |
| `incompat` | 1..62 | reservados (previstos: compresión de bloques, reciclado de WAL, valores separados, SST multiversión, estado de migración) | desconocido ⇒ `Incompatible` |
| `incompat` | 63 | `DRAFT`: archivo escrito por el borrador anterior a la congelación | ver §4.3 |
| `ro_compat` | 0..63 | reservados | desconocido ⇒ solo lectura |
| `compat` | 0..63 | reservados | desconocido ⇒ se ignora |

### 4.2 Reglas

- Los bits se evalúan **por archivo**, sobre todo archivo que la apertura lee: el `MANIFEST`, todas las SST referenciadas y todos los WAL vivos (§9). Los huérfanos no se validan.
- Toda estructura nueva que un lector v1 no entendería llega con un bit, en la palabra que corresponda; ADR-0013 lo registra.
- `Incompatible` y solo lectura se deciden **antes de cualquier mutación**: el directorio queda idéntico byte a byte (salvo la creación de `LOCK`).

### 4.3 Bit `DRAFT`

- Hasta la congelación, todo escritor pone `incompat` bit 63 en todos los archivos, y los lectores del borrador lo aceptan.
- Al congelar (WP14): los escritores dejan de ponerlo, el bit sale del conjunto conocido, se regeneran todos los vectores y se añade el vector negativo `draft-v1` (§13.2). Desde ese momento, una base creada con el borrador se rechaza con `Incompatible("pre-freeze draft format")` en lugar de leerse con reglas que pudieron cambiar.

## 5. Ranura AEAD

- `slot[40] = nonce[24] ‖ tag[16]` (24 bytes cubren XChaCha20-Poly1305; un nonce de 12 bytes, como AES-256-GCM-SIV, ocupa los 12 primeros y deja el resto a cero).
- Está **siempre** presente, justo antes del CRC, en cada bloque de SST y en cada registro de MANIFEST. En las tramas del WAL está presente **solo si** la cabecera de ese WAL tiene `AEAD` (un WAL nunca sobrevive a un cierre limpio, así que activar el cifrado no exige migrarlo, y los commits pequeños no pagan 40 bytes; decisión pendiente de firma en ADR-0013, con la alternativa «ranura siempre presente» descrita en una sola constante, `FRAME_SLOT_ALWAYS`).
- **AEAD-1.** Con `AEAD` desactivado, la ranura debe ser cero: si no, `Corruption`. La cubre el CRC, de modo que un bit flip aleatorio lo detecta el CRC y un archivo fabricado con CRC válido lo detecta esta regla. No queda ningún byte sin cubrir.
- Los datos asociados (número de archivo, desplazamiento, tipo de bloque) se especifican con ADR-0006; esta reserva no bloquea esa decisión.

## 6. WAL (`NNNNNN.wal`)

### 6.1 Disposición

```text
[0, 96)        cabecera común (KRNO_WAL, file_number, base_seq)
[96, ...)      trama*   (cada trama = un grupo de commits con un único CRC)
[..., EOF)     opcional: relleno de ceros (permite preasignar sin cambiar el formato)
```

### 6.2 Trama

| Despl. | Tamaño | Campo | Reglas |
|---|---|---|---|
| 0 | 4 | `payload_len` u32 | 1..=2^30 |
| 4 | 4 | `crc` u32 | `crc(file_number; bytes[0..4] ‖ bytes[8..32] ‖ payload ‖ slot?)` |
| 8 | 8 | `first_seq` u64 | primera trama del archivo: `base_seq`; después: `first_seq` + `count` de la trama anterior |
| 16 | 8 | `synced_len` u64 | bytes de **este archivo** que el escritor sabía duraderos cuando escribió la trama; `0` (ni la cabecera) o `96 ≤ synced_len ≤ despl. de la trama` |
| 24 | 4 | `count` u32 | commits de la trama, 1..=65 536; `first_seq + count − 1 ≤ 2^63−1` |
| 28 | 4 | `reserved` u32 | 0 |
| 32 | `payload_len` | `payload` | `count` commits (§6.3), consumidos exactamente |
| … | 40 | `slot` | solo si la cabecera tiene `AEAD` |

El commit `i` (desde 0) de la trama tiene la secuencia `first_seq + i`.

### 6.3 Commit y forma canónica

```text
commit := op_count varint (0..=2^24) ‖ op*
op     := 0x01 bytes(key) bytes(value)     PUT
        | 0x02 bytes(key)                  DELETE
        | 0x03 bytes(start) bytes(end)     DELETE_RANGE  [start, end), start < end
```

- **WAL-C1 (canonicalización).** El escritor procesa el `WriteBatch` en orden: `Put`/`Delete(k)` sustituye la operación de punto previa sobre `k`; `DeleteRange(a, b)` con `a < b` elimina las operaciones de punto previas con clave en `[a, b)` y añade el rango; `DeleteRange(a, a)` no tiene efecto. El resultado se escribe como **todos los rangos**, ordenados por `(start, end)` estrictamente creciente y sin duplicados, **seguidos de** las operaciones de punto con claves estrictamente crecientes.
- **WAL-C2.** Aplicar primero los rangos y después los puntos, todo con la misma secuencia, da el mismo estado que aplicar el lote operación a operación (SEM-3).
- **WAL-C3.** Un lote no vacío cuyas operaciones se anulan todas (p. ej. solo `delete_range(a, a)`) es un commit con `op_count = 0`: consume una secuencia y no cambia el estado. Un lote vacío no es un commit.
- **WAL-C4.** El lector comprueba la forma canónica (orden, unicidad, `start < end`, límites de §1.4); cualquier desviación en una trama con CRC válido es `Corruption`.

### 6.4 Reproducción de un WAL (lector)

Sea `expected` la secuencia esperada para el primer commit (para el WAL más antiguo, `last_seq` del MANIFEST + 1; para los siguientes, la siguiente a la última reproducida).

- **WAL-R1.** Si la cabecera es válida y `base_seq ≠ expected` ⇒ `Corruption`.
- **WAL-R2.** Las tramas se leen en secuencia, en flujo (bloques de lectura de 1 MiB; el archivo no se carga entero; una trama mayor se lee entera). La lectura se detiene en la primera trama, en el desplazamiento `P`, que esté incompleta (quedan menos de 32 bytes o la trama no cabe en el archivo), tenga `payload_len` fuera de 1..=2^30 o falle el CRC.
- **WAL-R3.** Una trama con CRC válido pero `first_seq ≠ expected`, `count` o `synced_len` fuera de rango, `reserved ≠ 0`, ranura no nula o carga mal formada (WAL-C4) ⇒ `Corruption`.
- **WAL-R4 (final limpio).** Si desde `P` hasta el final todos los bytes son cero, el WAL termina limpiamente en `P` (relleno).
- **WAL-R5 (cola rota frente a daño).** En otro caso, se buscan desde `P+1` hasta el final candidatos a trama en cada desplazamiento `q` con: `payload_len` en rango, la trama cabe en el archivo, `first_seq ∈ [expected, expected + (q − P)]`, `P < synced_len ≤ q`, y CRC válido. Si existe alguno ⇒ `Corruption` (los bytes en `P` eran duraderos cuando se escribió esa trama, así que el daño es posterior). Si no ⇒ **cola rota** en `P`. La cota de `first_seq` vale para tramas de grupo con cualquier número de commits: cada trama perdida en `[P, q)` tiene 32 bytes de cabecera y cada uno de sus commits ocupa al menos un byte de carga (un commit vacío, WAL-C3, es `op_count = 0`), así que antes de `q` hay menos de `q − P` commits.
- **WAL-R6 (cabecera rota).** Si la cabecera no valida por HDR-1, HDR-3 o HDR-2 con un *magic* desconocido, que no es de v1 ni del M0 (una cabecera que nunca se sincronizó puede quedar a ceros o con bytes ajenos mientras la primera trama sí llega al disco, pero nunca con el *magic* de otro tipo de archivo), se toma `P = 0` y se aplica la búsqueda de WAL-R5 (`first_seq ∈ [expected, expected + q]`) con `ctx = file_number` del nombre y tramas sin ranura (con ranura si `FRAME_SLOT_ALWAYS`): una trama con `synced_len > 0` ⇒ `Corruption`; si no hay ninguna, el WAL se considera **sin tramas** con cabecera rota (una trama con `synced_len = 0` bajo una cabecera rota pertenece a un commit cuyo `fsync` nunca terminó: no estaba confirmado en `Sync`, y en `Buffered` cae dentro del prefijo permitido).
- **WAL-R7.** Qué WAL pueden terminar en cola rota o tener la cabecera rota lo decide REC-10.

### 6.5 Reglas del escritor del WAL

- **W-1 (creación).** `CreateNew`, escribir la cabecera, `sync_dir`. No hay `sync_data` de la cabecera: se vuelve duradera con el primer `fsync` de una trama. Ninguna trama se escribe antes de que la entrada de directorio sea duradera.
- **W-2 (rotación en `Buffered`).** Antes de crear el WAL siguiente, `sync_data` del WAL actual (así solo el WAL más reciente puede quedar roto).
- **W-11 (`synced_len`).** El escritor mantiene `synced_len`: 0 al crear el archivo; tras cada `sync_data` con éxito, `synced_len := bytes escritos`. Cada trama lleva el valor vigente al escribirla. Un `fsync` fallido envenena el handle y ya no se escribe ninguna trama más en ese archivo (W-7).

Consecuencias (deben cumplirse y se prueban):

| Modo | `synced_len` de cada trama | Efecto en WAL-R5 |
|---|---|---|
| `Sync`, un escritor | desde la segunda trama, su propio desplazamiento | idéntico al M0: daño en una trama seguida de otra válida ⇒ `Corruption` |
| Group commit | el prefijo sincronizado antes de escribir el grupo | una trama = un grupo, un solo CRC: nunca hay «agujeros» dentro de un grupo |
| `Buffered` | el prefijo sincronizado en la última rotación o `sync()` | una cola rota tras un corte de energía se acepta (prefijo, I-03); tras un `sync()` posterior, ya no |
| Cabecera rota | primera trama con `synced_len = 0` | el WAL recién creado y roto cuenta como vacío |

**Preasignación y reciclado (sin regla nueva).** El escritor puede dejar el WAL como `cabecera ‖ ceros` de un tamaño dado, ya escrito y sincronizado, antes de la primera trama, de modo que el `fsync` de una trama sobrescribe bloques ya asignados y no confirma un cambio de tamaño. Es el relleno de §6.1 y WAL-R4: el lector se detiene en la primera trama inválida y acepta el resto solo si son ceros, así que ningún byte de un archivo válido cambia y el bit `incompat` reservado para el reciclado de WAL (§4) no se usa. Un archivo que se reutiliza para otro WAL (otro número, otra cabecera) **debe** haberse sobrescrito entero con ceros antes de renombrarse a su nombre canónico: las tramas de su vida anterior no se reproducirían (su CRC cubre otro número de archivo), pero tampoco son relleno, y un WAL que no es el último de la cadena y termina en bytes que no son ceros es una cola rota en mitad de la cadena (REC-10a). La implementación lo hace con un archivo aparte (`WAL.spare`, nombre no canónico que la recuperación ignora y borra) que solo se renombra cuando está completo y duradero.

## 7. SST (`NNNNNN.sst`)

### 7.1 Disposición

```text
[0, 96)              cabecera común (KRNO_SST, file_number, block_size)
[96, D)              bloques de datos, contiguos (ninguno si la tabla solo tiene rangos)
[rdel_off, +len)     bloque de rangos borrados (solo si range_fragments > 0)
[filter_off, +len)   bloque de filtro
[props_off, +len)    bloque de propiedades
[index_off, +len)    bloque de índice
[len − 80, len)      pie (80 bytes)
```

`D` = `rdel_off` si hay bloque de rangos; si no, `filter_off`.

### 7.2 Encapsulado de bloque (todos los tipos)

```text
payload ‖ slot[40] ‖ crc u32       crc = crc(file_number ‖ block_offset; payload ‖ slot)
```

La longitud de bloque que guardan el índice y el pie es `payload_len + 44`.

### 7.3 Bloque de datos

```text
entry*  := key_len varint ‖ seq varint ‖ kind u8 ‖ [value_len varint, solo PUT] ‖ key ‖ value
offsets := u32 × count        offsets[0] = 0; estrictamente crecientes; cada uno = inicio de una entrada
count   := u32 ≥ 1
```

- `kind`: 1 = PUT, 2 = DELETE (lápida de punto). Otro valor ⇒ `Corruption`.
- `seq` ∈ [1, 2^63−1].
- **SST-I1.** Una SST contiene **como mucho una versión por clave de usuario**: las claves son estrictamente crecientes dentro del bloque y en todo el archivo. (Las SST multiversión llegarían con un bit `incompat`.)
- Las entradas cubren exactamente `[0, inicio de offsets)`; no sobra ningún byte.

### 7.4 Bloque de rangos borrados

```text
count varint ≥ 1 ‖ fragment*      fragment := bytes(start) ‖ bytes(end) ‖ seq varint
```

- **SST-F1.** Fragmentos ordenados por `start` estrictamente creciente, `start < end`, sin solaparse (`end_i ≤ start_{i+1}`), `seq` ∈ [`smallest_seq`, `largest_seq`].
- **SST-F2 (escritor).** Cada fragmento lleva la **mayor** secuencia de las lápidas de rango que lo cubren (correcto porque una instantánea nunca ve una SST con secuencias mayores que la suya; ver SEM-5). Dos fragmentos adyacentes (`end_i = start_{i+1}`) con la misma secuencia se fusionan. Un punto de la misma SST cubierto por un fragmento de secuencia mayor no se escribe (lo descarta el flush o la compactación).

### 7.5 Bloque de filtro

```text
filter_kind u8 = 1 ‖ k u8 (1..=30) ‖ reserved u16 = 0 ‖ nbits u32 ‖ bits[nbits/8]
```

- `nbits` ≥ 64, múltiplo de 8; la carga mide exactamente `8 + nbits/8`.
- Contiene las claves de usuario de **todas las entradas de punto** (PUT y DELETE); los rangos no se insertan (un filtro no puede descartar un rango).
- Función de hash y sondeos congelados en §12.

### 7.6 Bloque de propiedades

TLV (§1.3) con etiquetas **estrictamente crecientes**. Las etiquetas 1–12 son obligatorias. Etiqueta desconocida < 1024 ⇒ `Corruption`; ≥ 1024 ⇒ se ignora.

| Tag | Campo | Tipo | Significado |
|---|---|---|---|
| 1 | `point_entries` | varint | entradas de punto (PUT + DELETE) |
| 2 | `point_deletes` | varint | entradas DELETE |
| 3 | `range_fragments` | varint | fragmentos del bloque de rangos |
| 4 | `smallest_seq` | varint | mínima secuencia de puntos y fragmentos |
| 5 | `largest_seq` | varint | máxima secuencia de puntos y fragmentos |
| 6 | `data_blocks` | varint | bloques de datos |
| 7 | `raw_key_bytes` | varint | suma de longitudes de claves de punto |
| 8 | `raw_value_bytes` | varint | suma de longitudes de valores |
| 9 | `smallest_key` | bytes crudos | `min(primera clave de punto, primer start)` |
| 10 | `largest_key` | bytes crudos | ver tag 11 |
| 11 | `largest_exclusive` | u8 | 1 si el último `end` de fragmento es mayor que la última clave de punto (o no hay puntos): `largest_key` = ese `end` y es **exclusivo**; si no, 0 y `largest_key` = última clave de punto |
| 12 | `creation_reason` | u8 | 1 flush, 2 compactación, 3 recuperación, 4 compactación dirigida |

### 7.7 Bloque de índice

```text
count varint (= data_blocks) ‖ ( bytes(last_key) ‖ offset varint ‖ len varint ) × count
```

`count = 0` si y solo si `point_entries = 0`.

### 7.8 Pie (80 bytes, en `len − 80`)

| Despl. | Campo | Despl. | Campo |
|---|---|---|---|
| 0 | `index_off` u64 | 8 | `index_len` u64 |
| 16 | `props_off` u64 | 24 | `props_len` u64 |
| 32 | `filter_off` u64 | 40 | `filter_len` u64 |
| 48 | `rdel_off` u64 | 56 | `rdel_len` u64 (ambos 0 si no hay bloque de rangos) |
| 64 | `magic` = `KRNO_SST` | 72 | `reserved` u32 = 0 |
| 76 | `footer_crc` = `crc(file_number; footer[0..76])` | | |

### 7.9 Validación

**Al abrir la tabla** (todas las sumas con comprobación de desbordamiento):

- **SST-O1.** Cabecera válida (HDR-1..10, tipo SST); `len` = `size` del `FileMeta`; `len` ≥ 96 + 80.
- **SST-O2.** Pie: CRC, `magic`, `reserved`.
- **SST-O3.** Disposición contigua: si hay rangos, `rdel_off + rdel_len = filter_off`; `filter_off + filter_len = props_off`; `props_off + props_len = index_off`; `index_off + index_len = len − 80`; `D` como en §7.1 y `D ≥ 96`. Sin bloque de rangos, `rdel_off` y `rdel_len` valen 0; si solo uno de los dos es 0, `Corruption`.
- **SST-O4.** Cada bloque meta: longitud ≥ 44, ≤ límite, CRC, ranura nula (AEAD-1), análisis exacto.
- **SST-O5.** Índice: las entradas recubren exactamente `[96, D)` en orden, cada `len` ≥ 55 (44 de encapsulado + 11 de la carga mínima), `last_key` estrictamente creciente, `count = data_blocks`.
- **SST-O6.** Propiedades: etiquetas 1–12 presentes y válidas (`largest_exclusive` ∈ {0, 1}, `creation_reason` ∈ 1..=4); `point_entries + range_fragments > 0`; `point_deletes ≤ point_entries`; `1 ≤ smallest_seq ≤ largest_seq ≤ last_seq` del MANIFEST; `smallest_key ≤ largest_key` (`<` si `largest_exclusive = 1`); todos sus campos iguales a los del `FileMeta` (§8.4).
- **SST-O7.** Filtro (§7.5) y rangos (SST-F1) bien formados; tantos fragmentos como `range_fragments`; cada fragmento cumple `smallest_key ≤ start` y `end ≤ largest_key` (con `largest_exclusive = 0` el último `end` no supera la última clave de punto, así que la condición es la misma en los dos casos).

**En cada lectura de un bloque de datos:**

- **SST-R1.** CRC, ranura nula, estructura (§7.3), claves estrictamente crecientes.
- **SST-R2.** Última clave del bloque = `last_key` del índice; primera clave > `last_key` del bloque anterior (bloque 0: ≥ `smallest_key`).
- **SST-R3.** Toda `seq` ∈ [`smallest_seq`, `largest_seq`].

**Solo en `verify()`** (lectura completa):

- **SST-V1.** La suma de entradas de todos los bloques = `point_entries`; DELETE = `point_deletes`; sumas de bytes = tags 7 y 8.
- **SST-V2.** `smallest_key` y `largest_key` coinciden con el primer y el último extremo reales.
- **SST-V3.** Toda clave de punto está en el filtro (un filtro incompleto escondería claves sin error).
- **SST-V4.** Ningún punto está cubierto por un fragmento de la misma tabla con secuencia mayor (SST-F2).

### 7.10 Reglas del escritor (deterministas, no las valida el lector)

- Tras añadir cada entrada, el bloque de datos se cierra si su carga (bytes de las entradas + 4 × `count` + 4) alcanza `block_size` (4096 en v1); una entrada mayor produce un bloque de una sola entrada.
- El filtro usa 10 bits por clave: `nbits = máx(n × 10, 64)` redondeado al múltiplo de 8 superior, `k = 7`.
- Con las mismas entradas, el mismo número de archivo y el mismo `db_id`, la salida es idéntica byte a byte (requisito de los vectores, §13).

## 8. MANIFEST

### 8.1 Disposición

```text
[0, 96)          cabecera común (KRNO_MAN, file_number = generation, first_edit_seq)
[96, ...)        registro*   registro 0 = SNAPSHOT; los demás se anexan
```

### 8.2 Registro

| Despl. | Tamaño | Campo | Reglas |
|---|---|---|---|
| 0 | 4 | `payload_len` u32 | 1..=256 MiB |
| 4 | 4 | `crc` u32 | `crc(generation; bytes[0..4] ‖ bytes[8..24] ‖ payload ‖ slot)` |
| 8 | 8 | `edit_seq` u64 | registro 0: `first_edit_seq`; +1 por registro (continúa entre generaciones); 1..=2^63−1 (§1.4) |
| 16 | 1 | `kind` u8 | 1 `SNAPSHOT`, 2 `SESSION_OPEN`, 3 `FLUSH`, 4 `COMPACTION`; 5 reservado (`MIGRATION`, Fase 4, llegará con un bit `incompat`); cualquier otro ⇒ `Corruption` |
| 17 | 1 | `flags` u8 | 0 |
| 18 | 6 | `reserved` | 0 |
| 24 | `payload_len` | `payload` | TLV (§8.3) |
| … | 40 | `slot` | §5 |

Tamaño mínimo de un registro: 24 + 1 + 40 = 65 bytes.

### 8.3 Campos (TLV)

Etiquetas **no decrecientes**; solo 10 y 11 pueden repetirse. Etiqueta desconocida < 1024 ⇒ `Corruption`; ≥ 1024 ⇒ se ignora.

| Tag | Campo | Valor |
|---|---|---|
| 1 | `next_file` | varint: próximo número de archivo sin usar |
| 2 | `last_seq` | varint: última secuencia contenida en las SST |
| 3 | `log_number` | varint: número **exacto** del WAL vivo más antiguo (o `next_file` si no hay ninguno) |
| 4 | `num_levels` | u8: v1 acepta 7; otro valor en 2..=16 ⇒ `Incompatible`; fuera ⇒ `Corruption` |
| 5 | `flags` | varint: bit 0 = `CLEAN`; otros bits ⇒ `Corruption` |
| 6 | `reason` | u8: 1 segundo plano, 2 dirigida (`compact_range`), 3 cierre, 4 movimiento trivial |
| 7 | `prev_generation` | varint: generación del MANIFEST reemplazado (0 al crear) |
| 10 | `add_file` | `FileMeta` (§8.4) |
| 11 | `delete_file` | `level u8 ‖ number varint` |

Campos por tipo de registro:

| Tipo | Obligatorios | Opcionales | Cualquier otro |
|---|---|---|---|
| `SNAPSHOT` | 1, 2, 3, 4, 5, 7 | 10* (por niveles crecientes; L0 de más nueva a más vieja; Ln por `smallest`) | `Corruption` |
| `SESSION_OPEN` | 1, 2, 3 | 10* (solo nivel 0: salidas del flush de recuperación, de más nueva a más vieja) | `Corruption` |
| `FLUSH` | 1, 2, 3 | 6, 10* (solo nivel 0) | `Corruption` |
| `COMPACTION` | 6 | 1, 10* (niveles ≥ 1), 11* | `Corruption` |

### 8.4 `FileMeta`

```text
level u8 ‖ number varint ‖ size varint ‖ point_entries varint ‖ range_fragments varint ‖
smallest_seq varint ‖ largest_seq varint ‖ flags u8 (bit 0 = largest_exclusive; otros ⇒ Corruption) ‖
bytes(smallest) ‖ bytes(largest)
```

Todos los campos deben coincidir con las propiedades de la SST (SST-O6).

### 8.5 Aplicación de registros

- `SNAPSHOT`: reemplaza el estado completo. Solo es válido como registro 0 de un archivo. Con `CLEAN`, exige `log_number = next_file`.
- `SESSION_OPEN`: fija 1, 2, 3; antepone los archivos a L0 en el orden dado; el estado deja de ser limpio.
- `FLUSH`: fija 1, 2, 3; antepone los archivos a L0 (0 o más; un flush de una memtable que solo recibió commits sin efecto no produce archivos pero sí sube `last_seq`).
- `COMPACTION`: fija 1 si está presente; borra cada `delete_file` (debe existir en ese nivel) y después añade cada `add_file` en su nivel, en la posición que le corresponde por `smallest` (nivel ≥ 1; nivel 0 ⇒ `Corruption` en v1). Un movimiento trivial es un borrado más un alta del mismo archivo con `reason = 4`.
- **MAN-A1.** `next_file`, `last_seq` y `log_number` nunca decrecen de un registro al siguiente.

### 8.6 Validación del estado (tras aplicar cada registro)

- **MAN-S1.** Números de archivo únicos y ≥ 1; todos < `next_file` ≤ 2^48−1; `1 ≤ log_number ≤ next_file`; `last_seq ≤ 2^63−1` (límite de formato de §1.4).
- **MAN-S2.** Cada archivo: `point_entries + range_fragments > 0`, `smallest ≤ largest` (`<` si `largest_exclusive`), `1 ≤ smallest_seq ≤ largest_seq ≤ last_seq`.
- **MAN-S3.** Niveles ≥ 1 ordenados y disjuntos: para archivos consecutivos `f`, `g`, `f` termina antes de `g.smallest` (si `f` es exclusivo, `f.largest ≤ g.smallest`; si no, `f.largest < g.smallest`).
- **MAN-S4.** L0: para dos archivos `i` antes que `j` cuyos rangos de claves se solapan (con la misma regla de exclusividad), `smallest_seq(i) > largest_seq(j)`. Archivos de L0 que no se solapan (p. ej. los de un mismo flush partido) pueden tener rangos de secuencia entrelazados.
- **MAN-S5.** `num_levels = 7`; todo `level` de `add_file` y `delete_file` < 7; ≤ 2^20 archivos por nivel. `num_levels` y los niveles se comprueban al decodificar los campos (§13.1).

Un lector no necesita revalidar el estado entero tras cada registro: el registro 0 se valida completo y cada registro siguiente solo en lo que cambia, con el mismo resultado, porque el estado anterior era válido y MAN-A1 impide que `next_file` y `last_seq` decrezcan. Basta con: MAN-S1 sobre los escalares y sobre los números añadidos (frente al conjunto de números del estado); MAN-S2 sobre los archivos añadidos; MAN-S3 sobre los vecinos de cada archivo añadido (borrar un archivo no desordena un nivel: «termina antes de que empiece el siguiente» es transitivo a través del archivo borrado, que cumplía MAN-S2); MAN-S4 sobre L0 si se le antepusieron archivos (borrar no lo rompe: es una regla sobre pares); MAN-S5 sobre los niveles que crecen. Comprobadas en ese orden, la regla informada es la misma. Así la reproducción cuesta lo que cambian los registros y no registros × archivos.

### 8.7 Reproducción del MANIFEST (lector)

- **MAN-R1.** Cabecera válida (HDR), `generation` ≥ 1 y registro 0 = `SNAPSHOT` válido con `edit_seq = first_edit_seq` y `prev_generation = generation − 1`. Si no (incluidos un archivo vacío, corto o truncado dentro del registro 0) ⇒ `Corruption` (I-09). El registro 0 se escribió antes del rename, así que nunca puede estar roto por una caída.
- **MAN-R2.** Se leen registros hasta el primero inválido, en `P`. Uno con CRC válido pero `edit_seq` o `kind` incorrectos, ranura no nula, campos que violen §8.3–§8.6 ⇒ `Corruption`.
- **MAN-R3.** Si `P` < longitud del archivo y desde `P` todo son ceros ⇒ final limpio. Si no, se buscan registros candidatos en cada desplazamiento > `P` con `edit_seq ∈ [expected, expected + ⌊(len − P)/65⌋ + 1]`, longitud en rango y CRC válido: si hay alguno ⇒ `Corruption` (cada registro se sincroniza antes de escribir el siguiente, W-3); si no ⇒ **cola rota** en `P`, aceptada.
- **MAN-R4.** El estado es **limpio** si y solo si el último registro válido es un `SNAPSHOT` con `CLEAN`.

### 8.8 Reglas del escritor del MANIFEST

- **W-3.** Un registro se escribe con un solo `write_at` y se sincroniza (`sync_data`) antes de escribir el siguiente, antes de borrar nada de lo que deja obsoleto y antes de publicar la nueva versión.
- **W-4.** Una SST se sincroniza (`sync_data`) y su entrada de directorio también (`sync_dir`) antes de que un registro la referencie.
- **W-7.** Nunca se anexa tras una cola inválida (ni en el MANIFEST ni en un WAL): se escribe un checkpoint o se crea un WAL nuevo.

### 8.9 Checkpoint

- **W-10.** Borrar un `MANIFEST.tmp` viejo; escribir `MANIFEST.tmp` (cabecera con `generation + 1`, `first_edit_seq` = siguiente `edit_seq`, y un único `SNAPSHOT`) → `sync_data` → `rename` a `MANIFEST` → `sync_dir`.
- Disparadores: `close()` (con `CLEAN`); apertura con cola rota (W-7); los bytes anexados superan `máx(4 MiB, 4 × tamaño del registro 0)`; `compact_range` (para que las claves del rango salgan del historial de ediciones).

## 9. Recuperación: tabla de decisión

La recuperación es parte del formato: estas reglas se congelan con él. Primero se **clasifica** el directorio y se valida todo lo necesario sin escribir nada; después, solo en lectura-escritura, se ejecuta el arranque de sesión (§9.4).

### 9.1 Sin MANIFEST

| # | Situación | Resultado |
|---|---|---|
| REC-1 | Directorio inexistente, vacío o con solo `LOCK` y/o `MANIFEST.tmp` | lectura-escritura con `create_if_missing`: crear (DIR-3); si no: `InvalidArgument("no database")` |
| REC-2 | Existen `.wal` o `.sst` canónicos | `Corruption` |
| REC-3 | Existen otros archivos | `InvalidArgument("not a Kerno database")`, sin tocar nada |

### 9.2 Con MANIFEST

| # | Situación | Resultado |
|---|---|---|
| REC-4 | Cabecera o reproducción inválidas (HDR, MAN-R); *magic* M0 | `Corruption`; `Incompatible` |
| REC-5 | SST referenciada ausente, de tamaño distinto, con `db_id`, número o propiedades distintos | `Corruption` |
| REC-6 | **Limpio** y existe una SST con número ≥ `next_file` | `Corruption` (prueba de un `SESSION_OPEN` perdido: W-8) |
| REC-7 | **Limpio** y existe un WAL con número ≥ `next_file`: con ≥ 1 trama válida ⇒ `Corruption`; sin tramas (vacío o con cabecera rota) ⇒ huérfano | |
| REC-8 | **Limpio**: cualquier archivo canónico no referenciado con número < `next_file` | huérfano |
| REC-9 | **Sucio** y no existe el WAL `log_number` | `Corruption("required WAL missing")` (W-1 y W-5 garantizan que existe; detecta un último `FLUSH` o `SESSION_OPEN` dañado cuyo WAL ya se borró) |
| REC-10 | **Sucio**: WAL vivos = los canónicos ≥ `log_number`, por número | regla de cadena, §9.3 |
| REC-11 | **Sucio**: SST no referenciadas (cualquier número) y WAL < `log_number` | huérfanos |
| REC-12 | `MANIFEST.tmp` | se ignora; se borra en lectura-escritura |
| REC-13 | Archivos desconocidos | se ignoran; nunca se borran |

### 9.3 Cadena de WAL vivos (REC-10)

Sean `W_1 < … < W_n` los WAL vivos y `k` el índice del último que tiene al menos una trama válida (`k = 0` si ninguno).

- **REC-10a.** `W_1, …, W_{k−1}`: cabecera válida y sin cola rota (pueden terminar en relleno de ceros); si no ⇒ `Corruption`.
- **REC-10b.** `W_k` puede terminar en cola rota (WAL-R5).
- **REC-10c.** `W_{k+1}, …, W_n` no tienen tramas; cada uno tiene la cabecera rota (WAL-R6) o una cabecera válida con `base_seq` = secuencia esperada tras `W_k`; si no ⇒ `Corruption`.
- **REC-10d.** Cada cabecera válida cumple WAL-R1 (continuidad de `base_seq`).

REC-10c es lo que hace **reentrante** la recuperación (I-11): el arranque de sesión crea el WAL nuevo *antes* de su registro en el MANIFEST (§9.4), así que una caída entre ambos pasos tras un cierre sucio con cola rota deja un `W_k` roto seguido de un WAL vacío, y eso debe seguir siendo recuperable. Lo prueba un test dirigido de caídas encadenadas (`chained_crash_during_session_start_after_torn_wal`).

### 9.4 Arranque de sesión (lectura-escritura)

- **S-1.** Clasificación y validación completas (§9.1–§9.3), sin escribir.
- **S-2.** Si el estado es sucio y la reproducción produjo commits: escribir las memtables reproducidas como SST de L0, partiendo cada vez que la memtable alcanza `write_buffer_bytes` (memoria de recuperación acotada); `sync_data` de cada una; `sync_dir`.
- **S-3.** Reservar el número `X` y crear el WAL `X` (W-1) con `base_seq = last_seq + 1`.
- **S-4.** Si el MANIFEST terminó en cola rota o supera el disparador de checkpoint: checkpoint (W-10) con un `SNAPSHOT` sin `CLEAN` y `log_number = X`. Si no: anexar `SESSION_OPEN{next_file, last_seq, log_number = X, add_file de S-2}` y `sync_data`.
- **S-5.** Publicar el estado; borrar huérfanos (REC-7, REC-8, REC-11) y un `MANIFEST.tmp` viejo; `sync_dir` si se borró algo.
- **S-6.** Arrancar los hilos de segundo plano.
- **W-8.** Ninguna trama se escribe en el WAL `X` antes de que el registro de S-4 sea duradero.

Coste de una reapertura limpia: `sync_dir` (S-3) + `sync_data` (S-4) = 2 sincronizaciones (M0: 3).

**Estado de la implementación (WP07, provisional hasta WP08).** El motor valida todo lo de S-1 (HDR-1..10 en cada archivo que lee, WAL-R1..R6, REC-10, SST-O1..O7) antes de escribir nada, pero todavía no anexa registros: cada cambio de la forma del LSM escribe una generación nueva del MANIFEST con un único `SNAPSHOT` (§8.9) y el arranque de sesión conserva el orden del M0 (SST de recuperación, MANIFEST nuevo con el `log_number` del WAL siguiente, borrado de los obsoletos y, al final, creación del WAL). Con ese orden el `base_seq` del WAL nuevo es el `last_seq` de un MANIFEST ya duradero, y una caída entre ambos pasos deja un MANIFEST sin WAL vivo, que se acepta: la regla REC-9 (WAL requerido ausente) y las del estado limpio (REC-6..REC-8) no se aplican hasta WP08. `close()` escribe el `SNAPSHOT` `CLEAN` (con `log_number = next_file`) después de la última compactación (W-9), pero nada lo exige todavía. Un bit `ro_compat` desconocido (HDR-7) da `Incompatible` en lugar de abrir en solo lectura, y un WAL con rangos o una SST con fragmentos dan `Incompatible` en lugar de ignorar las lápidas, hasta que existan la apertura de solo lectura (WP08) y los rangos (WP10).

### 9.5 Solo lectura, `verify()` e `inspect()`

- **RO-1.** Toman el `LOCK` exclusivo (`Locked` si la base está abierta); pueden crear `LOCK`; no hacen `create_dir_all`, `sync_dir`, borrados, checkpoints ni flush.
- **RO-2.** Aplican §9.1–§9.3 sin cambios; los WAL vivos se reproducen en memoria (la memoria es proporcional a los WAL vivos, acotados por el escritor a `(max_immutable + 1) × write_buffer` más un grupo). `verify()` no materializa nada: valida en flujo.
- **RO-3.** Huérfanos, `MANIFEST.tmp` y desconocidos se informan, nunca se borran.
- **RO-4 (carreras con instantáneas huérfanas).** Una instantánea que sobrevivió a un handle anterior puede borrar archivos obsoletos mientras otra apertura los inspecciona. Como un archivo solo pasa a obsoleto después de que un MANIFEST duradero deja de referenciarlo y los números nunca se reutilizan, la regla es: `NotFound` al abrir un archivo **no referenciado** ⇒ «huérfano desaparecido» (informativo); `NotFound` de uno **referenciado** ⇒ `Corruption`.

**Estado de la implementación (WP09).** `verify()` e `inspect()` existen como funciones de biblioteca de `kerno-storage` (la CLI llega en la Fase 2). `verify()` aplica §9.1–§9.3 con la misma función de clasificación que las aperturas, reproduce en seco cada WAL vivo, abre cada SST referenciada con SST-O1..O7 y lee todos sus bloques (SST-R1..R3, SST-V1..V4) sin pasar por la caché y sin búferes de archivo completo. El daño es un `Issue` con el id de la regla; `Err` queda para `Io`, `Locked`, `Incompatible` e `InvalidArgument` (directorio que no es una base). La clasificación REC-5..REC-10 informa solo la primera regla violada, como la apertura; el resto de comprobaciones sigue. Un huérfano que desaparece durante la comprobación se informa aparte (RO-4); una SST referenciada que desaparece es una violación de REC-5. `inspect()` lee solo cabeceras: una cabecera dañada se lista con la regla violada, una versión o un bit incompatibles son `Incompatible`.

## 11. Semántica congelada

- **SEM-1.** Cada commit no vacío recibe la secuencia siguiente (u64, desde 1, máximo 2^63−1); las secuencias son consecutivas entre tramas y entre WAL.
- **SEM-2.** Un lote se aplica atómicamente: todas sus operaciones tienen la misma secuencia.
- **SEM-3.** Orden dentro de un lote: la forma canónica (WAL-C1) aplica rangos y después puntos; en consecuencia, **un punto y un rango con la misma secuencia: gana el punto**.
- **SEM-4 (visibilidad).** Una entrada de punto `p@s` de la clave `k` es visible en la instantánea `S` si y solo si `s ≤ S`, es la versión más nueva de `k` con secuencia ≤ `S`, y **no existe** un fragmento `[a, b)@u` con `a ≤ k < b` y `s < u ≤ S`. Una lápida de punto visible significa «ausente».
- **SEM-5.** Toda SST de la versión que fija una instantánea `S` contiene solo secuencias ≤ `S`; por eso basta con una secuencia por fragmento en las SST (SST-F2), mientras que la memtable conserva todas.
- **SEM-6 (orden de fuentes).** Para claves solapadas: memtable activa > inmutables (de más nueva a más vieja) > L0 (MAN-S4) > L1 > … > L6; los niveles más profundos contienen datos estrictamente más viejos. Los límites de archivo incluyen la extensión de sus fragmentos.
- **SEM-7.** Una lápida de punto o un fragmento solo se descartan en compactación cuando ningún archivo de un nivel más profundo que la salida se solapa con ellos.

## 12. Constantes congeladas

- **Filtro bloom.** `h = fmix64(fnv1a64(key))`, con FNV-1a 64 (base `0xcbf29ce484222325`, primo `0x100000001b3`, xor y luego multiplicación por byte) y `fmix64(h)`: `h ^= h >> 33; h *= 0xff51afd7ed558ccd; h ^= h >> 33; h *= 0xc4ceb9fe1a85ec53; h ^= h >> 33` (multiplicaciones módulo 2^64). Sondeo `j` (0 ≤ j < k): `a_0 = h & 0xffffffff`, `a_{j+1} = a_j + ((h >> 32) | 1)` (módulo 2^64), bit `a_j mod nbits`. El bit `i` está en el byte `i / 8` con máscara `1 << (i % 8)`. Es la función de `spike-lsm/src/bloom.rs`.
- **Varints:** VAR-1..3. **Niveles:** 7. **Tamaño de bloque escrito:** 4096. **Cabecera:** 96 bytes. **Encapsulado de bloque:** 44 bytes. **Pie de SST:** 80 bytes. **Cabecera de trama:** 32 bytes. **Cabecera de registro:** 24 bytes.

### 13.4 Daño exhaustivo

En cada vector limpio de nivel 2: invertir cada bit de cada byte y truncar en cada desplazamiento. ## 15. Proceso de cambios del borrador y congelación

- Mientras rige el bit `DRAFT`, cambiar un byte del formato exige, **en el mismo PR**: una entrada en la tabla «Historial del borrador» de abajo, la actualización de este documento, la regeneración de los vectores afectados con la nota correspondiente en ADR-0013, y la reejecución de `spec_decoder_agrees` y de las suites de corrupción. Si el cambio toca checksums, la ranura AEAD, la cabecera o el borrado de datos, se marca la revisión del modelo de amenazas como pendiente.
- La congelación (WP14) exige ADR-0013 aceptado por el propietario y el modelo de amenazas revisado (R-07). Retira el bit `DRAFT`, regenera todos los vectores y fija la guardia. Después, cualquier cambio de bytes exige subir `format_version` o un bit de característica nuevo, más vectores y un ADR.

## 16. Diferencias con el prototipo M0 (`spike-lsm`)

| Aspecto | M0 | v1 |
|---|---|---|
| Identificación | WAL sin cabecera; SST solo con *magic* en el pie; MANIFEST con *magic* y versión dentro del cuerpo | cabecera común de 96 bytes con versión, bits, `db_id` y número de archivo |
| Registro del WAL | 16 bytes de cabecera, un commit por registro, bit 31 `SYNCED` | trama de 32 bytes por **grupo** de commits, `synced_len` (WAL-R5), lote canónico, `DELETE_RANGE` |
| WAL: reproducción | archivo entero en memoria | en flujo, 1 MiB por lectura |
| SST | trailer de bloque de 8 bytes, pie de 52 bytes, sin propiedades | encapsulado de 44 bytes con ranura AEAD, CRC con contexto, propiedades TLV, bloque de rangos, pie de 80 bytes |
| MANIFEST | instantánea completa en cada edición (2 sincronizaciones) | log de ediciones (1 sincronización), checkpoints por rename, marca `CLEAN` |
| `log_number` | `wal_number + 1` del último flush (puede no ser un WAL) | número exacto del WAL vivo más antiguo; un WAL requerido ausente es `Corruption` |
| L0 | orden no verificable | rangos de secuencia en `FileMeta`; MAN-S4 |
| Reapertura limpia | reescribe el MANIFEST y crea un WAL (3 sincronizaciones) | anexa `SESSION_OPEN` (2 sincronizaciones) |
| Límites | ninguno en el formato; lote ≤ 2 GiB | límites de formato y de API separados (§1.4) |
