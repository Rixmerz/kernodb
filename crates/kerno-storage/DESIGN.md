# kerno-storage: levelled LSM tree (Kerno engine, Phase 1)

> **Provenance.** Derived from `spike-lsm@0cba925`; format v1 in draft, never for user data (SAD §20.6).
>
> This crate was born as a copy of `spikes/storage/spike-lsm` with only renames ([Phase 1 design](../../docs/architecture/phase1-design.md) §5.1). Since WP07 it writes and reads **only** format v1 ([`docs/file-format/v1.md`](../../docs/file-format/v1.md)), frozen on 2026-10-31 (ADR-0013): the `DRAFT` bit is retired and a database created with the draft is rejected with `Incompatible`. The files of the M0 prototype are rejected with `Incompatible`. `spike-lsm` is frozen as the M0 baseline (ADR-0012); this document is updated with each Phase 1 package that changes the engine. Since WP08 the MANIFEST is an edit log, opening follows the session start S-1..S-6 with the pure function `recovery::classify`, read-only opening exists, and obsolete files are deleted by a dedicated thread. Since WP09, `verify()` checks an entire database without writing and `inspect()` reads the headers of its files. The pure codecs (no I/O) are in `src/format/` (WP06); `wal.rs`, `sst.rs`, `block.rs` and `manifest.rs` connect them to the `Vfs`.

A levelled LSM tree in the style of LevelDB/RocksDB that directly implements the harness contract `kerno_core::contract::Engine` (`KernoDb`, `KernoSnapshot`). It aims to be correct under crashes and media damage and reasonably fast, not tuned. All file I/O goes through `Arc<dyn Vfs>`.

## Configuration

`KernoDb::open(vfs, dir, &Config)`; `Engine::open` delegates with `Config::from(&Options)`, which takes durability, cache and write buffer from `Options` and leaves the rest at defaults. The default `Config` has the levers of condition 1 turned on, except `dynamic_base_level` and `file_picker = MinOverlap`, which stay off until the owner decides (see [Compaction](#background-work)); the `M0` profile (`CompactionConfig::m0` and unbounded close) reproduces M0.

| Field | Default | Effect |
|---|---|---|
| `access` | `ReadWrite` | `ReadOnly` opens without writing anything or launching threads (see [Read-only](#read-only)); without an existing database, `open` returns `InvalidArgument` and creates neither the directory |
| `create_if_missing` | `true` | with `false`, if `dir` has no `MANIFEST`, `open` fails before creating or modifying anything (neither the directory nor `LOCK`): `Corruption` if there are canonical WAL or SST files (a damaged database, as with `true`) and `InvalidArgument` otherwise (there is no database) |
| `durability` | `Sync` | durability mode of all commits of the handle |
| `cache_bytes` | 64 MiB | capacity of the block cache |
| `write_buffer_bytes` | 8 MiB | memtable size that triggers the switch and the flush (effective minimum 4 KiB); the target size of the SSTs and the target of L1 derive from it while `compaction` does not fix them |
| `max_immutable_memtables` | 4 | writers wait while this many memtables are pending flush (minimum 1; `0` is `InvalidArgument`) |
| `limits` | `Limits::default()` | API limits of a commit, checked before writing anything (v1.md §1.4): `max_key_len` 512 B, `max_value_len` 1 MiB, `max_batch_bytes` 64 MiB (bytes the commit occupies in the WAL) and `max_batch_ops` 2^20. They must be within the format maximums (16 KiB, 64 MiB, 2^30 and 2^24) and at least 1: otherwise `open` returns `InvalidArgument` without touching anything |
| `allow_unverified_platform` | `false` | the guarantees of `Durability::Sync` are verified only on Linux (ext4, xfs). On another platform, opening with `Sync` returns `InvalidArgument("durability not verified on this platform")` unless this is `true`; `Buffered` does not need it |
| `test` (hidden, tests only) | `TestConfig::default()` | `background`: `Threads` (background threads, as in M0) or `Inline` (see [Inline mode](#inline-mode-backgroundinline)); `db_id`: fixed identifier for a new database (by default, a random one), so that vectors and tests are reproducible |
| `group_commit` | `GroupCommitConfig::default()` | `enabled` (`true`), `max_group_bytes` (1 MiB of encoded commits per group; a larger commit forms its own group), `max_group_commits` (1024; format maximum 65 536) and `max_queued_bytes` (64 MiB: a commit waits before being queued while there are more bytes queued or in flight). With `enabled = false` the groups hold one commit (`Serial` profile). Zero values or values above the format maximum are `InvalidArgument` |
| `compaction` | `CompactionConfig::default()` | L0 thresholds (`l0_trigger` 4, `l0_slowdown` 8, `l0_stop` 12) measured by L0 **depth**, `level_multiplier` 10, rate throttling (`Rate`, 16 MiB/s initially) and the levers of the table below; `level_base_bytes`, `target_file_size`, `max_compaction_bytes` and `grandparent_overlap_bytes` are `None` and derive from the effective write buffer (4 ×, 1 ×, 25 × and 10 × the target file size), so a `Config` built with `..Config::default()` and another `write_buffer_bytes` keeps the geometry; `CompactionConfig::m0(wb)` turns off all the levers and sets those sizes explicitly |
| `close_budget` | `Bounded { max_bytes: 256 MiB, max_duration: Some(200 ms) }` | maximum compaction of a clean close, beyond the mandatory one (see [Clean shutdown](#clean-shutdown)); `Unbounded` is M0 |

The hidden module `testing` defines `Profile` and `Profiled<P>`: a different engine type per profile, which opens `KernoDb` with `Config::from(opts)` adjusted by `P::adjust`, to run the harness macros in several configurations without touching `Options`. Profiles: `Inline` (`Engine::name()` = `kerno-inline`, `test.background = Inline` and no time limit on close, so that the I/O sequence is deterministic; it also turns on `wal_preallocate`, `bytes_per_writeback = 1`, `dynamic_base_level` and `file_picker = MinOverlap` so that the sweeps go through their I/O) and `M0` (`kerno-m0`, `CompactionConfig::m0` and `CloseBudget::Unbounded`), with which the shared suite is also run so that a regression can be bisected down to one lever.

**Condition 1 levers** (`CompactionConfig`; [Phase 1 design](../../docs/architecture/phase1-design.md) §5.4; the value in parentheses is that of the `M0` profile):

| Field | Default | What it does |
|---|---|---|
| `flush_split` | `true` (`false`) | when writing a memtable, cuts the output between two consecutive keys whenever some L1 file lies entirely between them; the fragments of a flush do not overlap and enter together at the head of L0 |
| `l0_metric` | `Depth` (`Files`) | `l0_trigger`, `l0_slowdown` and `l0_stop` count the depth of L0 (maximum number of files containing the same key), not the files. As a bound against an L0 of many disjoint files (sequential keys), every 2 files count as at least one depth level |
| `l0_priority` | `false` (`false`) | with the metric ≥ `l0_slowdown`, L0 always wins. Off by default: WP04 rejected "L0 without priority" as the cause of the queue |
| `l0_partial` | `true` (`false`) | the L0 compaction takes the **oldest suffix** of L0 (the list runs from newest to oldest) as long as the L0 bytes plus the overlapping L1 bytes do not exceed `max_compaction_bytes`, and at least one file. It is safe because what remains is newer than everything that goes down |
| `max_compaction_bytes` | 25 × target | cap of the partial L0 compaction |
| `grandparent_overlap_bytes` | 10 × target (`u64::MAX`) | a compaction output is cut when it overlaps more than this many bytes of the level below the output level |
| `l0_trivial_move` | `true` (`false`) | the oldest L0 file with no overlap with L1 moves down to L1 without being rewritten |
| `slowdown` | `Rate { 16 MiB/s }` (`Sleep { 1 ms }`) | `Rate`: each commit waits `batch bytes / rate` (at most 100 ms); the rate is divided by 2 (minimum 1 MiB/s) while the metric grows with L0 throttling, and doubles again (up to the initial value) when it falls |
| `wal_preallocate` | `false` (`true`) | the WAL is `header ‖ zeros` of the size of the write buffer before its first frame, and an already flushed WAL is overwritten with zeros and kept as a spare instead of being deleted, so that a commit's `fdatasync` does not commit the file size (lever 1 of [f1-decision-cond1.md](../../docs/testing/f1-decision-cond1.md); details below) |
| `bytes_per_sync` | `None` (`None`; 1 MiB until the condition-1 tracking) | `sync_data` of the SST every so many bytes written (except in the compactions of close, which sync only at the end of each SST: there is no WAL to compete with). Replaced by default by `bytes_per_writeback`, which bounds dirty data without a barrier |
| `bytes_per_writeback` | 1 MiB (`None`) | every so many bytes written, the SST asks the file system to start writing back what was written (`File::start_writeback`: `sync_file_range(SYNC_FILE_RANGE_WRITE)` on Linux, nothing on other platforms), then waits for that same range (`File::wait_writeback`) and does nothing durable; it bounds the dirty data that the final `sync_data` finds in the same way as `bytes_per_sync`, but without a barrier. Where `bytes_per_sync` already syncs, it is not requested in addition (if both are set, `bytes_per_sync` wins; lever 5 of [f1-decision-cond1.md](../../docs/testing/f1-decision-cond1.md); details below) |
| `dynamic_base_level` | `false` (`false`) | with L1 empty, no compaction in flight towards L1, and L2 small enough that an L0 compaction with `l0_trigger` files fits in `max_compaction_bytes`, L0 is compacted directly into L2 (lever 4; a clean close does not skip L1; details below) |
| `file_picker` | `RoundRobin` (`RoundRobin`) | which file of a level above its target is compacted: `RoundRobin` (in turn by key) or `MinOverlap` (the one that rewrites the fewest bytes of the level below per byte that goes down; the turn breaks ties) |
| `heap_merge_threshold` | 8 (`usize::MAX`) | flush and compaction merges with more children use a binary heap |
| `max_background_compactions`, `max_subcompactions` | 1, 1 (1, 1) | compaction threads (`kerno-compact-<i>`; two compactions that read the same tables or write overlapping ranges in the same level never coincide) and parts into which an L0 compaction is split (cuts at L1 file boundaries; outputs installed with a single MANIFEST edit). WP05 conditionals: off because they showed no improvement in T1 beyond noise ([results](../../docs/testing/f1-queue-diagnosis.md#7-wp05-results)) |
| `close_subcompactions` | 8 (1) | `max_subcompactions` of the compactions of a clean close, which do not compete with any writer and whose mandatory part dominates the close of a random-order load. `Inline` mode ignores it and uses `max_subcompactions` (it launches no threads of its own) |

## Directory structure

| File        | Function |
|----------------|---------|
| `LOCK`         | `Vfs::lock` (exclusive open, `Error::Locked`); stateless, 0 bytes |
| `MANIFEST`     | shape of the LSM as an **edit log**: common 96-byte header, a `SNAPSHOT` and the records appended since then; atomically replaced by a new generation at each checkpoint |
| `MANIFEST.tmp` | exists only while a checkpoint is being written |
| `NNNNNN.wal`   | write-ahead log (WAL), one per memtable |
| `WAL.spare`    | spare WAL (`wal_preallocate`): zeros already written and synced that a rotation renames to its WAL; never a canonical name, so recovery does not replay it, and it is deleted on opening and on closing |
| `NNNNNN.sst`   | sorted table (SST) |

WAL and SST numbers come from a single increasing counter (`next_file`) and are never reused. On read-write opening, files that follow these patterns but are not alive (orphans: REC-7, REC-8, REC-11) are deleted, together with WALs already replayed and `MANIFEST.tmp`; a read-only opening reports them and does not touch them. Only canonical names count (DIR-1: `{n:06}.wal` or `{n:06}.sst` with `1 ≤ n ≤ 2^48−1`, exactly as they are written); files with other names, such as a loose `1.wal` or a number out of range, are unknown: they are not opened, not counted and not touched. A file that no longer exists when recovery tries to delete it (a previous handle's snapshot deleted it at the same time) is not an error.

**Creation and foreign files (DIR-2, DIR-3, REC-1..3).** Without `MANIFEST`, a database is created only if the directory does not exist or contains only `LOCK` and/or `MANIFEST.tmp` (what a crash during creation leaves behind). If there are canonical WAL or SST files, it is `Corruption` (REC-2); if there is any other file (the `data.kbt` of the B+ tree, the `log` of the reference engine, a `notes.txt`), `InvalidArgument("not a Kerno database")` without touching anything, not even `LOCK`. Creation does `create_dir_all` and `sync_dir` on the directories that contain the created ones **only when creating**, takes `LOCK` and writes the first MANIFEST (generation 1, empty `SNAPSHOT` and `CLEAN`) through `MANIFEST.tmp → sync_data → rename → sync_dir`; afterwards the normal start proceeds. The directory is listed again with `LOCK` held: that is the list recovery uses.

## Formats

The format is specified byte by byte in [`docs/file-format/v1.md`](../../docs/file-format/v1.md); here only what the engine does with it.

- **Common header** (96 bytes, §3) in the three file types: `magic`, `format_version`, `compat` / `ro_compat` / `incompat` bits, `db_id`, file number (the generation in the MANIFEST) and one field per type (`first_edit_seq`, `base_seq`, block size), with its own CRC32C. It is validated in full (HDR-1..10) on every file that is read, before interpreting anything else and before writing anything. The engine no longer sets any `incompat` bit; the draft's `DRAFT` bit, an unknown `incompat` bit, `AEAD` or `format_version > 1` is `Incompatible`; unknown `compat` bits are ignored (and a rewritten file does not keep them); an unknown `ro_compat` bit (HDR-7) opens the whole database read-only (`KernoDb::is_read_only` returns `UnknownRoCompat { file, bits }`).
- **WAL** (§6): frame with a 32-byte header + payload, **one frame per commit group** (WP12; a one-commit group when group commit is off or there is only one writer). Each frame carries `first_seq`, `count` (the commits of the group, with consecutive sequences) and `synced_len` (W-11): the prefix of the file that the writer knew to be durable when writing it. The CRC takes the file number as context. The payload is the commit in canonical form (WAL-C1).
- **SST** (§7): header, data blocks, filter, properties, index and an 80-byte footer. Each block is wrapped as `payload ‖ 40-byte AEAD slot (zeros) ‖ crc`, with the block offset as CRC context. It keeps one version per user key and one sequence per entry. If the table has range tombstones, a **range block** (§7.4) with the fragments, which stays resident like the index and the filter (see [Range tombstones](#range-tombstones-and-compact_range)). No prefix or block compression; the binary search inside a block uses the offset array.
- **MANIFEST** (§8): record 0 `SNAPSHOT` with `next_file`, `last_seq`, `log_number`, `num_levels` (7), `flags` (`CLEAN`), `prev_generation` and a `FileMeta` per file (level, number, size, point entries, range fragments, sequence range, key ends, which include the extent of the fragments, and whether the last one is exclusive). L0 is listed from newest to oldest; L1 and beyond, sorted and without overlaps. The other records are `SESSION_OPEN` (session start), `FLUSH` and `COMPACTION` (with its reason: background, directed — `compact_range` —, close or trivial move). Meaning of the fields:
  - `last_seq`: the newest commit contained in the SSTs.
  - `log_number`: the **exact** number of the oldest live WAL (W-5); the WALs numbered `>= log_number` contain, in order, the commits after `last_seq`. After a clean shutdown (`CLEAN`) it is `next_file`.

A change to the shape of the LSM is **one appended record**: one `write_at` and one `sync_data` (W-3), before deleting anything it makes obsolete and before publishing the new version. `ManifestWriter` keeps the append handle, the position of the next record and the current `edit_seq`; a failed append poisons the handle and it never appends again after a possibly invalid tail (W-7).

A **checkpoint** (W-10) replaces the file with a new generation holding a single `SNAPSHOT`: `MANIFEST.tmp → sync_data → rename → sync_dir`, with generation + 1 and the next `edit_seq` (which continues across generations). It is written instead of the next append when (a) the MANIFEST ended in a torn tail on opening, (b) the appended bytes exceed `max(4 MiB, 4 × the size of record 0)` and (c) on demand (`TestHooks::checkpoint`); and with `CLEAN` on close. The file size is thus bounded by that of the shape of the LSM and does not grow with the history.

## Commit path

Every non-empty commit goes through the commit queue (`commit_queue.rs`, see [Group commit](#group-commit-and-sync)); what follows is the work of the **leader request** for its group.

1. In the calling thread, the batch is checked against `Config::limits` (operations, keys, values and bytes; `InvalidArgument` before writing anything, without consuming a sequence or poisoning) and canonicalised (WAL-C1; the canonical form is what is written **and** what the memtable applies). A poisoned handle returns `Poisoned`, and an empty batch returns the last **published** sequence, without going through the queue. The commit is queued while holding the write slot (`txn_gate`), taken only during enqueueing.
2. The head request is the leader. It takes the writer mutex, takes from the queue a FIFO group (up to `max_group_bytes` / `max_group_commits`) and, from here on, works for the whole group:
   - With sequence 2^63−1 already used, the commits that do not fit fail with `InvalidArgument("commit sequence exhausted")`, without writing or poisoning; those that fit go on.
   - `make_room` **once** (a group never crosses two WALs): it checks the write buffer and applies backpressure (see below). If the memtable exceeds `write_buffer_bytes`, it switches memtable:
     - In `Buffered` mode, first `sync_data` of the old WAL (and `durable_seq` becomes the last confirmed sequence).
     - A memtable that reaches 4 096 range tombstones is also full, whatever its size: each read pays for each tombstone of each memtable it consults. A single commit may exceed that number; the next one switches memtable.
     - Creates the new WAL (header with `base_seq = last_seq + 1`, with `sync_data` of the header: W-1) and then `sync_dir`.
     - Publishes a new `Version` in which the old memtable is immutable.
3. Assigns consecutive sequences `last + 1 ..= last + n`, encodes **one frame** (`count = n`, current `synced_len`) and writes it with a single `write_at`. It does `sync_data` in `Sync` mode or if there is a `sync()` request in the group (which sets `synced_len` to the bytes written).
4. Applies the batches to the memtable in sequence order: a `crossbeam_skiplist::SkipMap` keyed by (user key ascending, sequence descending) and tombstones, plus the list of range tombstones `(start, end, seq)` appended-only behind an `RwLock`. It applies the canonical form, so repeated keys within a batch were already reduced to the last operation, and ranges go in before points (WAL-C2).
5. Publishes `last_seq` (and `durable_seq`) **once**, under the state mutex and **after the `fsync`** in `Sync` mode (W-12, I-16): no reader observes a sequence that a power cut could undo. A snapshot takes `(Arc<Version>, last_seq)` under the same mutex, so capturing it is atomic with respect to publication. Readers with an older seq ignore the newer entries of the skip list.
6. Delivers each member its result (its sequence), passes leadership to the next request and wakes whoever is waiting for room in the queue.

**`Sync` commit fsyncs: one `sync_data` (the WAL's) per group**, that is, exactly 1 with a single writer and fewer than 1 with concurrent writers. Further amortised:

- One `sync_dir` per memtable switch, that is, every `write_buffer_bytes`.
- In the background, per flush: 3 syncs (`sync_data` of the SST, `sync_dir` and `sync_data` of the `FLUSH` record; M0 and WP07 paid 4). Per compaction: `sync_data` of each output, one `sync_dir` and the `sync_data` of the `COMPACTION` record. A clean reopening costs 2 (`sync_dir` of the new WAL and `sync_data` of the `SESSION_OPEN`).

The frame header (32 bytes) is paid once per group; with a single writer it adds 16 bytes per commit compared with M0.

**Backpressure:**

- With the L0 metric ≥ `l0_slowdown` (8 by default), each commit waits once (`SlowdownPolicy::Sleep`: up to 1 ms, as in M0; `Rate`: `bytes / rate`, until the delay is met or the metric drops; `Off` disables it). In `Inline` mode there is no throttling.
- With ≥ `max_immutable_memtables` immutable memtables (4 by default) or the L0 metric ≥ `l0_stop` (12 by default), the commit blocks until a background thread makes progress.
- The thresholds are in `Config::compaction` (`CompactionConfig`); `CompactionConfig::m0(write_buffer)` reproduces the M0 constants.
- Each block is an **episode**: it is counted once when entering the wait, by reason (memtables or L0), with its duration; intermediate wake-ups do not count (M0 counted wake-ups).

## Group commit and `sync()`

`commit_queue.rs` is the state machine of the queue, **with no I/O**, written over the `crate::sync` facade (`parking_lot` normally; `loom` with `--cfg kerno_loom`). `db.rs` puts the I/O in the leader's body.

- **Queue.** `Mutex<State>` with a FIFO `VecDeque` of requests and, per request, its own `Mutex<Slot>` + `Condvar` (`Waiting` → `Leader` → `Done(result)`). The head request is the leader; the thread whose request finds the queue empty leads without waiting (fast path, no regression with one writer). A leader directs **one** group — itself included — and completes it: `complete` takes the group out of the queue, delivers the results and promotes the next request. There is only one group in flight.
- **Lock order:** `txn_gate → queue → request slot` and, in `db.rs`, `txn_gate → queue → writer → manifest → state`. The queue lock is never held during I/O nor while requesting another: the leader takes `writer` and **then** takes the group, so that commits arriving while it waits for `writer` (for example, for an inline flush) join it.
- **Failure.** If the write or the `fsync` of a group fails, the handle is poisoned: the group's members receive `Io` (an `io::Error` is built per member: it is not `Clone`) and the queued ones that were not in the group, `Poisoned`, with nothing more written; those waiting for room and those arriving later receive `Poisoned` from the queue. The leader's body runs inside `catch_unwind`: a panic poisons (`"commit leader panicked"`), fails the group with `Io` and wakes everyone; nobody waits for a leader that no longer exists.
- **Backpressure.** `enqueue` waits while the queued or in-flight bytes exceed `max_queued_bytes`; the maximum number of bytes queued at once is, by construction, `max_queued_bytes` plus one commit.
- **Draining.** `CommitQueue::drain` waits until nothing is queued or in flight. `begin_write` uses it with the write slot taken: as blind commits take the slot only to enqueue, whoever holds it and has drained the queue has the pipeline to itself (see [Transactions](#read-modify-write-transactions)).
- **`sync()`.** Enqueues a request with no batch (0 bytes). The leader does `sync_data` only if there is an unsynced frame (`WalWriter::needs_sync`, not `synced_len < bytes written`: a WAL with only a header has nothing to make durable) and returns `durable_seq`, which is the last confirmed sequence. In `Sync` mode it does no I/O. A failed `sync()` poisons like a failed commit; on a poisoned handle it returns `Poisoned` without I/O. A read-only handle will return `ReadOnly` once it exists (WP08: today `open` rejects `AccessMode::ReadOnly`).
- **`durable_seq`** (in `State`, published together with `last_seq`): equal to `last_seq` in `Sync`; in `Buffered`, the last sequence covered by a `sync()` or by the WAL rotation (W-2) and, on opening, the one recovered.
- **Linux semantics after a failed `fsync` (FL row of the [failure matrix](../../docs/architecture/failure-matrix.md)).** In `Buffered`, a failed `fsync` of a `sync()` discards on Linux the pending WAL pages: `Buffered` commits after the last successful `sync()` may be lost even though they were confirmed, and the recovered state remains a prefix not earlier than that `sync()`.
- **Check.** `loom` (`RUSTFLAGS="--cfg kerno_loom" cargo test -p kerno-storage --release --lib commit_queue`) explores leader hand-over, poisoning propagation, the `txn_gate` drain and backpressure with three threads (bound of 3 preemptions per model); the same scenarios run with real threads in every build. In addition, `tests/group_commit.rs` holds the leader at an exact point with `HookVfs` and a stress of 10^4 commits with random delays and yields (with `--features deadlock_detection`, the `parking_lot` detector watches the engine's locks).

## Read-modify-write transactions

`KernoDb::begin_write` returns a `WriteTxn` (`src/txn.rs`; ADR-0002, [Phase 1 design](../../docs/architecture/phase1-design.md) §5.7). It is **serialisable by exclusion**: the transaction holds the write slot (`txn_gate`) for its whole life, so nobody else commits between its reads and its commit (D-03).

- **Start.** `begin_write` checks that the handle is writable and healthy (`ReadOnly`, `Poisoned`), takes the slot, **drains the queue** (`CommitQueue::drain`: what was queued earlier finishes and publishes; in `Sync` it may cost the `fsync` of the group in flight) and takes a registered snapshot of the last published state. As nobody can enqueue while the slot is taken, that state remains the last one until the transaction ends (`read_seq`).
- **Reads.** `get`: the overlay point; if not, the ranges deleted by the transaction itself (return `None`); if not, the snapshot. `scan`: merges pages of the snapshot, without the keys hidden by the transaction's ranges (it pages again until `limit` is filled: a whole hidden page does not cut the traversal short), with the overlay, which wins on a tie.
- **Overlay.** Three views of the same writes: the final value of each key written one by one (`BTreeMap<Vec<u8>, Option<Vec<u8>>>`; a deleted range removes the entries it covers), the list of non-empty ranges (they hide keys of the snapshot; what was written after them wins) and the ordered record of operations, which is what gets committed. Before the commit the transaction touches only its overlay: no shared state.
- **Limits.** `put`, `delete` and `delete_range` check `Config::limits` at once (`InvalidArgument`; the write is not done and the transaction remains usable), also the number of operations and the key and value bytes of a batch: the overlay is bounded by the maximum batch. The exact encoding is checked on commit (`InvalidArgument`, nothing written, slot free).
- **Commit.** Validates and canonicalises the record like any batch (WAL-C1), **enqueues while holding the slot**, releases it and waits for its group; returns the sequence. A transaction with no writes returns the current sequence and consumes none (one with only `delete_range(a, a)` is a non-empty batch: it consumes one). When the commit starts, the read snapshot is released, so that a commit waiting for room, its group or the `fsync` does not retain the version it read nor the files that compactions replace in the meantime. The commit does exactly the I/O of a blind commit (`transactions_do_the_io_of_blind_commits`).
- **End without commit.** `abort` and `Drop` (also when unwinding the stack due to a user panic) write nothing, consume no sequence and release the slot. A leader panic during commit poisons as in any commit.
- **Costs by design.** A long transaction **blocks all writers** (other `begin_write`, blind `commit` and `sync`); reads are not blocked. Transactions do not chain with each other. `txn_gate_wait_micros` exposes the wait. Calling `begin_write`, `commit` or `sync` on the thread that holds the transaction is a deadlock; debug builds turn it into a panic (`Gate`, `db.rs`).
- **Lock order.** `txn_gate → queue → writer → manifest → state`; the snapshot registry and the draft's deletion queue are leaves. `begin_write` takes `txn_gate` and then the queue lock (`drain`), never the other way round; the leader does not take `txn_gate`.
- **Tests.** `txn_test_suite!` (module `shared_txn`) with `KernoDb` and the `Inline` profile, validated first on `Emulated<LogEngine>`; `tests/txn.rs` (leader panic during a transaction's commit, slot wait, counters, batch limits, read-only, scenario B with transactions and crash sweeps); `prop_txn_overlay_matches_model` (`tests/model.rs`) compares each `get` and `scan` of the transaction with a model after every operation; `differential_rmw` compares it with the oracle and with the other engines; `rmw_counters` (T9) measures its cost.

## Background work

There are two threads: the **flush** one (`kerno-flush`) and the **compaction** one (`kerno-compact-0`). They share a condition variable with the writer. MANIFEST edits are serialised with a mutex of their own: each holder computes the new levels from the last durable ones, appends its record (or writes the checkpoint that applies) and then installs a new `Version`. A third thread, `kerno-delete`, deletes obsolete files (see [Versions, snapshots and file lifetime](#versions-snapshots-and-file-lifetime)).

**Flush** (first the oldest immutable memtable):

1. Writes the newest version of each key into one or more new L0 SSTs (several if `flush_split` cuts around L1 files, see `flush.rs`), and then `sync_data` and `sync_dir`.
2. Appends a `FLUSH` record with the tables, as a group, at the head of L0 (a flush of a memtable whose commits had no effect produces no tables, but it advances `last_seq`), `last_seq = max(last_seq, mem.max_seq)` and `log_number` = the number of the WAL of the next oldest memtable, or of the active one: the **exact** oldest live WAL (M0 used `wal_number + 1`, which might not be a WAL).
3. Installs the new version and deletes the WAL (W-5: only after the record is durable). The deletion is best effort; recovery removes the leftovers.

**Compaction** (levelled, as in LevelDB):

- L0 scores `metric / l0_trigger` (the metric is the depth, or the number of files in the `M0` profile); Ln (n = 1..5), `bytes / (level_base_bytes × level_multiplier^(n−1))`; with the default values, `bytes / (4 × write_buffer × 10^(n−1))`. The highest score ≥ 1 wins; with `l0_priority` and the metric ≥ `l0_slowdown`, L0 wins.
- The L0 compaction merges the oldest suffix of L0 that fits in `max_compaction_bytes` (all of L0 when `l0_partial` is off) and the L1 files that overlap it; if the oldest file does not overlap L1 and `l0_trivial_move` is on, it moves down a level without being rewritten. With `dynamic_base_level`, the output goes to L2 (and the overlapping files are those of L2) while L1 is empty and L2 is small (see [below](#l0-below-an-empty-l1-dynamic_base_level)).
- The Ln compaction takes one file, chosen in turn by key (or, with `file_picker = MinOverlap`, the one that rewrites the fewest bytes of Ln+1 per byte that goes down), plus those of Ln+1 that overlap it. A file with no overlap is moved down a level without being rewritten.
- Output files are cut at `target_file_size` (by default, the effective write buffer) and when they overlap more than `grandparent_overlap_bytes` of the level below the output level.
- The merge keeps only the newest version of each key. Older snapshots keep reading the input files through their own `Version`.
- A tombstone is discarded when no file in a level below the output level has a key range that contains the key.
- The outputs are synced, then `sync_dir`, then the `COMPACTION` record is appended (the `delete_file` of the inputs and the `add_file` of the outputs, with the reason; a trivial move is a deletion and an addition of the same file, reason 4) and then the version is installed. Only then are the inputs marked obsolete.
- On shutdown, the compaction in progress is abandoned and its partial outputs are deleted.
- If the append fails, nothing is deleted and the handle is poisoned: the record may have reached the disk, so the outputs could be referenced. The next recovery decides with what the surviving MANIFEST says, and deletes the files that it does not reference.

### Inline mode (`Background::Inline`)

Test-only configuration (`Config::test.background`, profile `testing::Inline`; [Phase 1 design](../../docs/architecture/phase1-design.md) §1 point 6 and §5.1). No thread is launched. `make_room` applies no slowdown or blocking (there is no one to wait for): if the active memtable is full, the same commit, with the writer mutex held, switches it (step 2 of the commit path), writes the oldest immutable one to L0 with the usual flush and runs all the compactions that `pick` chooses until none is pending; only then does it write its own record into the new WAL. The lock order remains `writer → manifest → state`, and the round-robin positions of these compactions live in the writer's state. Close is the usual one, also on the calling thread. If one of those steps fails, the commit itself returns that step's error (`Io`, or `Corruption` if the compaction finds a damaged SST) and the handle is poisoned: from then on, `Poisoned`.

Without threads, the sequence of file-system operations depends only on the calls: the `every_point` sweeps number the same in every run, the `SimVfs` traces repeat operation by operation (`inline_io_trace_is_deterministic`) and the `proptest` model test reduces and reproduces any failure.

### Test hooks (`TestHooks`) and phase probe

`KernoDb` implements `kerno_core::contract::TestHooks` (also through `hooks()`, hidden):

| Hook | `Threads` | `Inline` |
|---|---|---|
| `wait_idle` | waits until there is no pending or running flush and no pending or running compaction, and until the draft has attempted all the queued files (failing ones are counted and do not hold the wait) | deletes what is pending and returns |
| `flush` | switches the active memtable if it has commits and waits for the flush thread to write all the immutables | the same, in the calling thread; does not compact |
| `compact_once` | compactions run on their own: waits as `wait_idle` and returns `true` if at least one finished while it waited (among them, any pending or running at the time of the call; there may be more than one) | runs at most one compaction; `true` if one was pending |
| `compact_range` | see [`compact_range`](#compact_range); always in the calling thread | the same |
| `checkpoint` | writes a new MANIFEST generation with the current shape (W-10), without `CLEAN` | the same |

All of them return `Poisoned` if the handle is poisoned and `ReadOnly` (except `wait_idle`) if it is read-only. The engine's code labels its I/O with `kerno_core::probe::phase`, which `SimVfs::trace` records with each operation: `create` (opening a new database: syncing the directories that contain it and initial recovery), `session` (opening an existing database: recovery), `commit`, `rotate`, `flush`, `compact`, `compact_range` (the directed compactions and the deletion of their inputs), `close`, `checkpoint` (every write of a new MANIFEST generation, also the `CLEAN` one on close; see [`harness::matrix`](../kerno-testkit/src/harness/matrix.rs) for the correspondence with the rows of the failure matrix) `delete` (deletion of obsolete WALs after a `FLUSH` and of obsolete SSTs by the `kerno-delete` thread; with `wal_preallocate`, the flushed WAL is also recycled here) and `wal_spare` (preparation of the spare WAL in the middle of a memtable). The session-start operations (S-2..S-5) carry `session` and those of the final close step (WAL), `close`.

## Range tombstones and `compact_range`

Condition 2 of ADR-0001 as **mechanism**; no retention policy and no guarantee of physical erasure (C-11, R-52; ADR-0009 accepted on 2026-11-12, option 3: no guarantee of physical erasure). Semantics in [v1.md §11](../../docs/file-format/v1.md) (SEM-3..SEM-7): `delete_range(start, end)` deletes `[start, end)`; a point `p@s` is hidden in the snapshot `S` if some fragment `[a, b)@u` covering it satisfies `s < u ≤ S` (with the same sequence the point wins).

- **Memtable.** The memtable's tombstone list keeps each `(start, end, seq)`: a reader at snapshot `S` ignores those with a higher sequence, as it ignores points. It is turned into fragments (`format::rangedel::fragment`: disjoint, with the highest sequence covering each piece) when it is flushed and when a `scan` is done.
- **SST.** The range block stores sorted, disjoint fragments with **one** sequence each, the highest (SST-F2): a snapshot never sees an SST with sequences higher than its own (SEM-5), so one is enough. The file extents (`smallest`, `largest`) include the extent of the fragments; if the last fragment ends beyond the last point key, `largest` is that end and is **exclusive** (`largest_exclusive`). Every comparison of neighbouring files (`Table::ends_before`, like `FileMeta::ends_before`, MAN-S3) takes exclusivity into account: two files of a level may touch at a key if the first ends at it without containing it. SSTs without points are allowed.
- **`get`.** Walks the sources from newest to oldest with `max_tomb`, the highest sequence (`≤ S`) of the tombstones covering the key in the sources already seen. The fragments of a source count **before** its bloom filter (which says nothing about ranges); the first point found is returned if `s ≥ max_tomb` and is `None` if `s < max_tomb`; if the next file has `largest_seq < max_tomb`, the search ends with `None`. The point in the memtable itself is checked **after** its tombstones (an earlier proposal returned it first: incorrect).
- **`scan`.** Each source with fragments provides a sorted list and a cursor that only moves forward (`rangedel::CoverCursor`); for the newest version of each key, the highest sequence covering it is taken, and the key is hidden if that exceeds the point's. With no fragments in any source there are no cursors and the cost per key is that of M0.
- **Flush and compaction.** They do not write a point that a fragment of their inputs covers with a higher sequence; they cut the fragments they keep at each cut of the output (size, grandparent, *flush split*, subcompaction range), so that the extents of the files of a level stay disjoint even when the fragment is wide (`rangedel::FragmentSplitter`); and they discard a fragment when no file below the output level overlaps it (`DeeperLevels::range_may_overlap`; always when writing to L6). A file with fragments never moves down by trivial move: the rewrite is where they disappear. A table with only fragments is a valid output.
- **WAL and recovery.** WAL replay passes ranges to the memtable, just as it does points (WAL-C1, WAL-C4); recovery (S-2) flushes the replayed ranges as fragments.

### `compact_range`

`KernoDb::compact_range(start, end) -> CompactRangeReport { files_rewritten, bytes_read, bytes_written, pinned_files, pinned_bytes }` (and the hook `TestHooks::compact_range`; `ReadOnly` on a read-only handle):

1. If the active memtable has anything, it switches memtable and waits for all immutables to be written (the data leaves the WAL, which is retired after its `FLUSH`).
2. Compacts level by level, **in the calling thread** and claiming its files like a background thread (`Busy`; it waits if it collides with a compaction in progress): at each step, the shallowest level above the last one that has files overlapping the range moves to the next level, until none does. From L0 it takes the oldest suffix that contains every overlapping file (what remains is newer than what goes down). A file with no overlap below only moves without being rewritten if it has no tombstone; the others are rewritten, which is where the tombstones, and the points they cover, stop being in the files. The compactions carry the reason `directed` in the MANIFEST and `creation_reason = 4` in the SSTs; their I/O goes in the `compact_range` phase (DC row of the failure matrix).
3. Writes a MANIFEST **checkpoint**: the old generation names in its records the key ends of the files that went away.
4. Removes from the cache the blocks of the replaced tables.
5. The report counts as `pinned_*` the input tables that are still referenced (`Arc` count > 1) by a snapshot or by a version that a snapshot retains; they are deleted when the last reference is dropped.

### What can survive `compact_range`

It is a mechanism to take data and tombstones out of the live files, **not** an erasure guarantee:

- **Files retained by snapshots** (`pinned_files`, `pinned_bytes`): while a snapshot or a version it retains is alive, its tables remain on disk with what the tombstones covered.
- **Freed blocks of deleted files.** Deleting a file does not overwrite its blocks; they remain on the medium until the file system reuses them (and an SSD may keep them longer).
- **Memory and cache.** The engine purges the replaced tables from the block cache, but the content may still be in process memory (returned values, snapshots, buffers) and in the operating system's page cache.
- **The WAL.** It is retired only after the `FLUSH` of its memtable; `compact_range` rotates and flushes before compacting, so the WALs with data in the range are deleted, but the deletion does not overwrite either. This holds for the default configuration: with `wal_preallocate` a flushed WAL is overwritten with zeros and kept as a spare (section "Preallocated and recycled WAL"). That is not an erasure guarantee: the spare is a live file of the directory, and the overwrite does not reach blocks that the file system or the medium may have kept.
- **Point tombstones on the last level.** A table with point tombstones that a background trivial move carried to the last level (M0 behaviour) keeps those tombstones: `compact_range` does not compact L6 against itself.
- **Copies of the directory** made outside the engine and the history of the file system.

ADR-0009, accepted on 2026-11-12 with option 3, fixes what the engine promises: immediate logical deletion and removal of the live files on compaction, if no open snapshot older than the deletion retains them. It does not promise physical erasure nor a backup deadline, and cryptographic erasure is left to ADR-0006 (Phase 4). `tests/suppression_survival.rs` (E9A-01) measures in the test scenario the two points of the list that are files of the directory (the snapshots and the WAL); the rest is not measured.

## Versions, snapshots and file lifetime

`Version = { active memtable, immutable memtables (from newest to oldest), levels of Arc<Table> }`. Each memtable switch, flush and compaction installs a new version. A snapshot holds an `Arc<Version>` and its seq.

- **Get:** active memtable, then the immutables, then L0 from newest to oldest, then one candidate file per deeper level (binary search over the end of each file, exclusive or not). In each file it checks the key range, **the range fragments**, the bloom filter and then the index. With range tombstones it walks the sources with `max_tomb` (see [Range tombstones](#range-tombstones-and-compact_range)).
- **Scan:** a k-way merge (linear minimum over a small number of sources) that delivers the newest visible version of each key. Point tombstones are skipped, as are keys covered by a range tombstone newer than their version; all `Bound` combinations are handled, and empty or inverted ranges return nothing.

**Snapshot registry** (`snapshots.rs`). `Arc<SnapshotRegistry>` shared by the engine and by each snapshot (it survives the handle: dropping or closing the handle with live snapshots is safe): `BTreeMap<(seq, id), Instant>`; `Drop` unregisters. The write transaction reads from a registered snapshot. Metrics: `snapshots_live`, `snapshot_oldest_seq`, `snapshot_oldest_age_ms` and `snapshot_retained_bytes` (0 without snapshots). The last one adds up the bytes of the tables marked obsolete that are still alive (it rises in `Table::mark_obsolete`, falls in `Table::drop`) and those of the memtables that left the current version when written and are still alive (it rises in `Memtable::retire`, when the flush is installed; falls in `Memtable::drop`). It is what only the snapshots' versions retain; an ongoing compaction or flush also retains it for an instant.

An SST is deleted when its last reference is dropped, but only if the table is marked obsolete, and that happens only after a durable MANIFEST record stops referencing it. `Table::drop` no longer deletes (W-13): it **enqueues the path** in the shared `Deleter` (`deleter.rs`). While the engine lives, a `kerno-delete` thread deletes what is enqueued and retries failures with growing wait (10 ms up to 1 s), counting `delete_failures`; in `Background::Inline` there is no thread and whoever enqueues deletes at once (failures are retried on the next call). When the handle is closed (or dropped), the deleter stops, tries once everything left and, from then on, each `drop` deletes inline, as in M0. Thus a reader that drops the last snapshot never pays for deletion while the engine is alive. A file whose deletion keeps failing becomes an orphan, and the next recovery deletes it. Metrics: `obsolete_bytes_pending` (bytes enqueued and not yet deleted), `obsolete_files_deleted` and `delete_failures`.

## Recovery (on every open, including that of a new database)

Everything is first **classified and validated**, without writing; only afterwards is anything written.

0. Before touching anything, `open` rejects with `InvalidArgument` an invalid `Config` (limits outside the format, `max_immutable_memtables = 0`, `Sync` on an unverified platform) (`ReadOnly` access is no longer rejected). It lists the directory. Without `MANIFEST`: `Corruption` if there are canonical WAL or SST files (REC-2), `InvalidArgument("not a Kerno database")` if there are other files (REC-3), `InvalidArgument` if there is no database and `create_if_missing` is `false` (or the access is `ReadOnly`, which never creates); in all these cases nothing is created or modified. With `create_if_missing` and an empty directory (or with only `LOCK` and `MANIFEST.tmp`) the database is created (see Creation above).
1. Creating the directory and syncing its parents happens **only when creating** and before `LOCK` (`LOCK` lives inside the directory). The directory that contains the database's directory is synced, and the one that contains each directory that `create_dir_all` has just created (first it checks which are missing): without a single metadata journal, a directory entry is durable only when the directory that contains it is synced (found by the per-directory durability model of WP03b: with `/data/apps/db` on an empty disk, a power cut could delete the whole database after confirmed `Sync` commits). In a relative path of a single component, that directory is the current one, `.`. These syncs are mandatory: if one fails, the opening fails. The ancestors further up need not have changed, and syncing them can fail for reasons unrelated to the database (`sync_dir` opens the directory and needs read permission, which is missing on an ancestor that can only be traversed, such as a `home` in mode 0711 or an app's data on Android; a read-only file system may not support directory `fsync`). But an earlier opening of a new database may have created part of the chain (`create_dir_all` creates one level at a time) and failed or died before syncing them. As it is not known which ones, on every new database the ancestors above the highest mandatorily synced one are also synced, without guarantee, from the bottom up. The climb stops silently only when the error shows that the process cannot sync that directory (`PermissionDenied`, `ReadOnlyFilesystem`, `Unsupported`). Any other error, such as an `EIO`, makes the opening fail: after a failed `fsync` it is not retried assuming the data reached the disk (ADR-0002, I-10). Then it takes the lock and lists the directory again: nobody else can change it, and that list is the one used for recovery.
2. Reads the MANIFEST (HDR-1..9, MAN-R*, MAN-S*): corruption is reported, never treated as "start empty"; an M0 *magic*, an unknown version or an unknown `incompat` bit are `Incompatible`. Opens each referenced SST (SST-O1..O7): header (with `db_id` and file number, HDR-10), size, footer, layout, meta blocks, index, properties, filter and all the fields of the `FileMeta` (including the sequence range, which must fit in `last_seq`).
3. Replays the WALs `>= log_number` in order of number, streaming (1 MiB reads; the file is not loaded whole). Each log starts at the sequence following the previous one (`base_seq`, WAL-R1) and the frames carry consecutive sequences:
   - A frame that verifies but has an incorrect sequence, `count`, `synced_len` or payload is `Corruption` (WAL-R3, WAL-C4).
   - Reading a log stops at the first incomplete frame or one with incorrect CRC at `P`. If everything from `P` onwards is zeros, it is padding; if not, it looks for later valid frames with `P < synced_len ≤ q`: if there is any, the damage was durable → `Corruption`; if not, it is a torn tail (WAL-R5).
   - A broken header (WAL-R6: HDR-1, HDR-3 or an unknown *magic*) with a valid frame behind it is `Corruption` whatever its `synced_len` (the writer syncs the header before the first frame); if there is no frame, the log counts as empty (a creation cut by a crash).
   - Which logs may end torn is decided by REC-10 over the whole chain: those before the last one with commits are intact (valid header, no torn tail), that one may have a torn tail and the later ones have no commits.
4. **Classifies** (`recovery::classify`, a pure function over the listing, the MANIFEST replay and what the WAL scan said; v1.md §9.1–§9.3). With the shape of the database, applies REC-4..REC-13:
   - REC-5: a referenced SST that is missing, or of another size, `db_id` or properties, is `Corruption`.
   - **Clean** state (the last record is a `SNAPSHOT` with `CLEAN`): an SST numbered `next_file` or higher is `Corruption` (REC-6: a lost `SESSION_OPEN`); a WAL numbered `next_file` or higher with any frame is `Corruption`, and without frames (empty or with a broken header) it is an orphan (REC-7); everything else unreferenced is an orphan (REC-8).
   - **Dirty** state: the WAL `log_number` must exist (REC-9, "required WAL": a damaged last `FLUSH` or `SESSION_OPEN` whose WAL was already deleted appears as `Corruption`, not as a smaller database); the live WALs are those `>= log_number` and form a chain (REC-10a–d); unreferenced SSTs and WALs lower than `log_number` are orphans (REC-11).
   - `MANIFEST.tmp` is ignored and, read-write, deleted (REC-12); unknown files are ignored and never deleted (REC-13).
5. Only if all of the above went well, **writes** (`recovery::apply`; session start S-2..S-6):
   - **S-2.** Rereads the live WALs —the classification keeps no commits— and writes an L0 SST every time the replayed memtable reaches `write_buffer_bytes` (recovery memory is bounded by the buffer, not by the log; a recovery reads each log twice); `sync_data` of each one and a `sync_dir`.
   - **S-2b.** `sync_data` of the newest WAL that had frames. Its frames may not be durable (`Buffered`, or a process that died with the OS cache intact) and the WAL of the next step will assert, with its `base_seq`, that they exist; until `SESSION_OPEN` is durable the old chain is what a recovery would read, and a power cut in that window would leave a gap between both (found by `single_io_failure_at_every_point_buffered` with threads).
   - **S-3.** Creates the WAL `X` (`next_file`, reusing no number in the directory) with `base_seq = last_seq + 1`: header and `sync_dir` (W-1), **before** its record. REC-10c makes that window re-entrant.
   - **S-4.** Appends `SESSION_OPEN { next_file, last_seq, log_number = X, tables of S-2 }` and `sync_data`; or, if the MANIFEST ended in a torn tail or exceeds the size trigger, writes a checkpoint without `CLEAN` with `log_number = X` (W-7, W-10). No frame is written before this record is durable (W-8): the state stops being clean before the first frame.
   - **S-5.** Deletes the orphans, the replayed WALs and `MANIFEST.tmp`; `sync_dir` only if it deleted anything.
   - **S-6.** Launches the background threads and the deleter.

Consequences:

- Nothing is ever appended after a torn tail: the old log is not written again and a MANIFEST with a torn tail is replaced.
- The state that `open` reports is durable before `open` returns (SST + `SESSION_OPEN`, or the checkpoint).
- A crash at any step is recovered with the same rules: before S-4, the old MANIFEST and its WALs remain in force (the S-2 SSTs are orphans and the WAL `X` is a WAL with no frames after the last one with frames, REC-10c); after it, the new state. `chained_crash_during_session_start_after_torn_wal`, `recovery_makes_replayed_frames_durable_before_the_new_wal` and the sweeps of `manifest_log.rs` check this.
- A failure before S-4 (a full disk while writing an SST) changes no file that already existed.
- If the levels exceed their target, the compaction is scheduled right after opening (in `Inline` mode, it runs at the next memtable switch or at close).

Recovery follows the same path on read-only openings up to and including step 4; see [Read-only](#read-only).

## Clean shutdown

Follows W-9:

1. Stops and waits for the flush and compaction threads. If the handle is poisoned, returns `Poisoned`.
2. If the active memtable received commits, it **rotates** it (new empty WAL: W-1, W-2): thus the last `FLUSH` can name a WAL that exists as the oldest live one.
3. Flushes the immutables, from the oldest to the newest, with a `FLUSH` record each.
4. `compact_for_close`, in the calling thread: first, **always**, compacts L0 until its metric falls below `l0_trigger` (the same choice as normal work, except that with `l0_partial` it takes only the oldest files needed to bring the metric below: with a random-order load each L0 file drags all of L1 along, so the ones left are bytes that the close neither rewrites nor deletes); then, one compaction at a time while there are bytes and time left in `close_budget` (the bytes read and written by all the compactions of the close, mandatory ones included; the time, from the start of the close) and some level exceeds its target. A compaction that starts within the byte budget may end above it; one that, at the pace of the previous compactions of the same close (deletion of its inputs included), would end after `max_duration` is not started. These compactions use `close_subcompactions` and do not do the intermediate `sync_data` of `bytes_per_sync`. What is left pending is picked up by the scoring after the next opening: the format records no debt. `close` returns a `CloseReport { duration, flushed_bytes, compacted_bytes, budget_exhausted, l0_files, l0_depth }` (the contract's `Engine::close` discards it). `max_duration: None` makes the close deterministic. (Found by the adversarial review of M0: before, the close abandoned the compaction in progress and one more file was added to L0, so many short sessions made L0 grow without limit and each reopening started with late compactions.)
5. **`CLEAN` checkpoint** with `log_number = next_file`: a new generation with a single record. It is always written after the last compaction (it used to be written before the close's compactions and rewritten after them).
6. Deletes all the WALs (W-5: only now that the checkpoint is durable) and `sync_dir`. When the handle is dropped, the deleter tries one last time the obsolete files that remain.

After a clean shutdown the directory holds only `LOCK`, `MANIFEST` (a single record) and SSTs, and all their bytes have a checksum. That is why an inverted bit or a truncation produces an error instead of an older commit, and why the extra files have meaning: an SST or a WAL with frames numbered `next_file` or higher reveals a session whose `SESSION_OPEN` was lost (REC-6, REC-7). A crash at any point of the close leaves a state that is recovered without loss (`crash_at_every_point_of_close`).

## Read-only

`AccessMode::ReadOnly`, or an unknown `ro_compat` bit in any file the opening reads (the MANIFEST, the referenced SSTs, the live WALs), opens the database without writing (v1.md §9.5; invariant I-18): it takes the exclusive `LOCK` (`Locked` if another handle, read or write, holds it), classifies the directory with the same function as the read-write opening, opens the SSTs and replays the live WALs **into a single in-memory memtable** (memory is proportional to the live WALs). It does no `create_dir_all`, `sync_dir`, deletions, checkpoints or flush, launches no threads and creates nothing (the `LOCK` may be created). Orphans, `MANIFEST.tmp` and unknown files are reported (`recovery_orphans`, hidden) and not touched.

- `commit` (even with an empty batch), `begin_write`, `sync`, `compact_range`, `TestHooks::flush`, `compact_once` and `checkpoint` return `Error::ReadOnly` (`Inner::check_writable`).
- Reads, snapshots and `wait_idle` work; `close` writes nothing.
- `KernoDb::is_read_only()` returns `Requested` or `UnknownRoCompat { file, bits }` (the first file with unknown bits). With both reasons, `Requested` wins.
- The internal `Writer` of a read-only handle carries a marker WAL (`WalWriter::read_only`) whose writes would fail without touching the disk; no entry point ends up using it.

## `verify()` and `inspect()`

They are library functions (`kerno_storage::verify`, `kerno_storage::inspect`; the CLI arrives in Phase 2, C-01) and **do not write**: the only thing they can create is `LOCK` (v1.md §9.5, RO-1; invariant I-18). Each takes the exclusive `LOCK`, so they return `Locked` if another handle or process has the database (`tests/process_lock.rs`). A directory that is not a database (nonexistent, empty or with foreign files) is `InvalidArgument` and nothing is locked or created; data files without a MANIFEST are a damaged database (REC-2) and are reported.

`verify(vfs, dir, &VerifyOptions { deep, check_wal })` follows these steps:

1. Reads the MANIFEST (HDR, MAN-R*, MAN-S1..S5, MAN-A1) with `manifest::read_structured`, which keeps the rule broken instead of formatting a message.
2. Scans the WALs that the recovery table needs with `format::wal::scan_wal` and a null receiver (the dry replay: it validates each frame and applies nothing) and classifies the directory with `recovery::classify`, the same function as the openings. `classify` returns a `RuleViolation { file, rule, detail }`; the openings turn it into `Corruption` with the same message as always, and `verify` copies it into an `Issue`. With `check_wal = false` the WALs are not read and the rules that depend on their content are not applied (REC-7, REC-10).
3. Opens each referenced table with the checks SST-O1..O7 against the MANIFEST's `FileMeta` (and, right after, the part of SST-V3 that can be done without reading data, `format::sst::check_filter_holds_index_keys`: the last key of each data block, which the index already has in memory, must be in the filter; `Table::open` and `verify()` call it, not `open_sst`, so as not to alter the frozen rule order of v1.md §13.1 that the vectors fix; a filter zeroed or overwritten block by block does not open nor report clean, not even without `deep`) and, with `deep`, reads **all** the data blocks (SST-R1..R3) and runs `SstVerifier` (SST-V1..V4: totals of entries and bytes, key ends, every key in the filter, no point covered by a newer fragment of the same table). It reads directly from the file, block by block, bypassing the cache (`fill_cache = false`): memory does not grow with the database, and no buffer is larger than the table because the index (SST-O5) bounds each block.
4. Reports the orphans with their size, `MANIFEST.tmp` and the unknown files, without deleting anything (RO-3). An orphan that disappears while it is being checked (a previous handle's snapshot deleted it) goes to `vanished_orphans` and is not a problem; a **referenced** table that disappears is `REC-5` in `issues` (RO-4).

**Bloom filter (finding F-E9A-03-1, [threat model](../../docs/security/threat-model.md) §6.6).** A filter whose bits were rewritten with the CRC recomputed hides keys from `get` without error (`scan` does not use the filter). The opening rejects the coarse case (SST-V3 over the last keys of the index: one hash per block, no data read), and `verify()` with `deep` detects any filter missing a key of the table, because it probes the filter with each key it reads (SST-V3, without key bytes, I-29). **Remaining limit:** if the filter only lacks interior keys of a block, the opening accepts it and `get` answers "does not exist" without error; making `get` distrust it would read the data block and remove the purpose of the filter, and against a deliberate rewrite only authentication (AEAD, ADR-0006, pending) would help. The engine does not promise that protection: whoever needs it runs `verify()` with `deep`. A saturated filter (extra bits) is not damage to the format and only costs performance.

The damage is reported in `VerifyReport::issues` (`file`, `offset`, `rule`, `detail`, without key or value bytes) and the check continues with the next file; the classification stops at the first REC rule broken, as the opening does. `Err` is reserved for what prevents saying anything: `Io`, `Locked`, `Incompatible` (a version, an `incompat` bit, encryption or the M0 format are not damage) and `InvalidArgument`. An `Issue` with the same rule in the same file is reported only once. A torn tail of the MANIFEST or of the last WAL (MAN-R3, WAL-R5) is accepted as in the opening and only noted (`manifest_torn_tail`, `WalReport::torn_tail`).

`inspect(vfs, dir)` reads only the headers (96 bytes per file, or its `header_len` if it declares more) of the MANIFEST, of the WALs and of the canonical SSTs and returns `FormatInfo { files }` with, per file, the type, the length and the version, the `compat` / `ro_compat` / `incompat` bits, the `db_id` and the file number. A damaged header is not an error: the file appears with `header: None` and the broken rule in `problem` (a WAL whose creation was cut by a crash has a legitimately invalid header, WAL-R6). A version or a bit that the engine cannot read is `Incompatible`, as in the opening.

Tests: `tests/verify.rs` (clean, read-only byte by byte, each inverted bit, truncations, filter missing a key, filter rewritten with valid CRC (`tests/open_properties.rs`), disorder between blocks, totals that do not add up, orphans, vanished orphans, locking, options), `tests/crafted.rs` (files with valid CRCs that break a structural rule; no operation reserves more than the engine does for an honest database nor twice the largest file), `tests/damage.rs` (damage during use and after crashes: error or correct data, never wrong data) and `tests/process_lock.rs` (two real processes).

## Integrity coverage

| Data | Protection | Checked |
|------|------------|--------------|
| Header of each file | own crc; version, bits, `db_id` and file number | every time the file is read, before any write |
| WAL frame | crc with the file number as context; sequence continuity; `synced_len` | replay |
| Data block | crc with (file number, offset) as context, so a moved block does not verify; structure; increasing keys; last key = index key; sequences within the table's range | every read from disk |
| Filter, properties and index blocks | crc with context; AEAD slot zeroed; exact parsing; the filter contains the last key of each data block (partial SST-V3) | opening |
| Footer | crc with the file number; *magic*; layout consistency | opening |
| SST versus MANIFEST | size, entries, key and sequence ranges, `db_id` | opening |
| MANIFEST record | crc with the generation as context; invariants MAN-S1..S5 | opening |
| Table totals, key ends, full filter, points versus own fragments (SST-V1..V4) | full read | `verify()` only |

Any discrepancy returns `Error::Corruption`, except in `verify()`, which reports it as an `Issue`. Corruption found by a background compaction poisons the handle.

## Durability modes

- **Sync:** a commit is durable when it returns (one `fsync` per group).
- **Buffered:** no sync per commit, but the records are written with `write_at` before `commit` returns, so a process crash loses nothing confirmed. On a power cut, the recovered state is a **prefix of commits**, never older than the state the last `open` reported. This holds because:
  - the old WAL is synced before a new one is created, so only the newest log can have gaps, and replay stops at the first gap;
  - the SST and the MANIFEST are durable before any WAL they replace is deleted;
  - recovery makes its result durable before returning: the SSTs and the `SESSION_OPEN` (or the checkpoint) and, before creating the new WAL, the old WAL whose frames it replayed (S-2b).

  `sync()` (ADR-0002) makes durable what is confirmed up to that moment and returns the durable sequence (see [Group commit](#group-commit-and-sync)).

## Errors and poisoning

Any I/O error on the commit path (append, sync, memtable switch), a leader panic or an error in a background thread (flush, compaction, MANIFEST write) poisons the handle. From then on, `commit`, `sync`, `snapshot` and `close` return `Poisoned` until the database is reopened. The members of the failed group receive `Io`. Snapshots taken earlier keep working over what remains readable.

`Drop` activates the shutdown flag, wakes everyone who is waiting and waits for the flush and compaction threads, which end on shutdown, on poisoning or on their first failed I/O; then it stops the deleter (see above). A panic in a background thread is caught and poisons the handle.

## Statistics (`Engine::stats`)

`KernoDb::metrics()` returns a typed snapshot (`Metrics`, in `src/metrics.rs`); `stats()` flattens it with stable names and keeps all those of M0 (`write_stalls` now counts episodes).

- **Shape:** `l{0..6}_files` / `l{0..6}_bytes`, `l0_depth` (maximum number of L0 files overlapping at one key), `l0_files_max`, `memtable_bytes`, `immutable_memtables`, `last_seq`, `durable_seq`, `block_cache_bytes`.
- **Writes:** commits, groups (`commit_groups`, `group_commits_max`), `queued_bytes_max`, WAL bytes and syncs, memtable switches and their duration within the commit (`memtable_rotation_micros`, `_max`).
- **Commit phases:** log2 histograms (each power of two split in four: percentiles with error < 25 %) of `queue`, `make_room`, `wal_write`, `wal_sync`, `apply` and the total, with `commit_<phase>_{count,micros,max_micros,p50_micros,p99_micros}`. `wal_sync` is further split into `wal_sync_busy` (with a flush or a compaction writing) and `wal_sync_quiet`. `queue` and `total` have one sample per commit; `make_room`, `wal_write`, `wal_sync` and `apply`, one per group (the leader writes them, under the writer mutex). Each phase costs an `Instant::now()` and three relaxed atomic additions.
- **Blocking:** `stall_episodes_{memtable,l0}`, `stall_micros_{memtable,l0}`, `stall_micros_max`, `slowdown_commits`, `slowdown_micros`; the M0 names `write_stalls`, `write_stall_micros` and `write_slowdowns` are derived from them.
- **Ranges:** `range_fragments` (fragments in the files of the current version), `range_tombstones_dropped` (fragments that a compaction did not write because no deeper file overlaps them) and `covered_points_dropped` (points it did not write because a newer fragment covers them).
- **Background:** flushes and flush bytes (including those of close and recovery), `flush_micros_max`, compactions, `compaction_micros_max`, trivial moves, bytes read and written by compaction, tombstones discarded, L0 compactions with their input bytes and L1 files rewritten (totals and maxima), `compactions_while_l0_slowdown` (compactions of deep levels chosen while L0 is throttling) and `pending_compaction_bytes` (bytes above the target of L1 to L5, plus all of L0 when it reaches `l0_trigger`). Also `sst_writeback_hints` (writeback requests from the SST writers, `bytes_per_writeback`) and `l0_base_level_skips` (L0 compactions whose output went below an empty L1, `dynamic_base_level`).
- **Reads:** bloom checks, negatives and false positives; block cache hits and misses. Each counter is spread over 16 slots aligned to 64 bytes (one per thread, by turn) that are summed on read, so that concurrent readers do not compete for the same cache line.
- **Maintenance:** `manifest_writes` (records appended plus checkpoints), `manifest_records`, `manifest_checkpoints`, `manifest_bytes` (current file size), `obsolete_files_deleted`, `obsolete_bytes_pending` (bytes enqueued and not yet deleted) and `delete_failures`.
- **Snapshots:** `snapshots_live`, `snapshot_oldest_seq`, `snapshot_oldest_age_ms`, `snapshot_retained_bytes` (see [Versions](#versions-snapshots-and-file-lifetime)).
- **Transactions:** `txns_committed` (`commit` returned a sequence, also for an empty transaction), `txns_aborted` (`abort` or `Drop`; a failed commit counts in neither) and `txn_gate_wait_micros` (total time threads waited for the write slot in `begin_write`, blind commits and `sync`; taking a free slot is not measured).
- **Opening:** `last_open_clean` (1 if no WAL commit was replayed) and `last_open_replayed_bytes` (bytes of the valid frames replayed, without the log headers).

## Known limitations / what would change for production

The Phase 1 packages attack several of them ([Phase 1 design](../../docs/architecture/phase1-design.md) §5).

- **MANIFEST.** The edit log grows to `max(4 MiB, 4 × record 0)` before being replaced by a checkpoint, and opening replays it in full: with many edits per session, the start-up cost grows up to that limit. The size trigger has no test that exercises it at production scale beyond `manifest_checkpoint_bounds_file_size`.
- **Writes.** The commit is copied into the request so that the leader can read it while its owner waits (one copy of keys and values per commit). The leader of a group leads **one** group: under load, each group costs a thread hand-over. Each memtable switch costs a `rename` of the spare WAL plus `sync_dir` (with `wal_preallocate = false`, a creation plus `sync_dir`). A group waiting in `make_room` (a flush stall) delays all its members.
- **Compaction.** By default a single compaction thread and no subcompactions (`max_background_compactions` and `max_subcompactions` exist but are off). There are no dynamic level sizes. Throttling by rate looks only at L0, not at the debt of the deep levels.
- **SST format.** No prefix compression, no block compression, no partitioned index or filter, and no format versioning beyond the magic numbers.
- **Memory and files.** The index and filter of each table stay resident and all tables stay open, so memory grows with the number of files. The block cache only holds data blocks.
- **Start-up cost.** An opening after a dirty shutdown reads the live WALs twice (classify and replay) and rewrites what was replayed as L0 SSTs; one after a clean shutdown replays nothing and costs two syncs. It is simple and makes the result of `open` durable.
- **Reads.** Merges of more than 8 children use a binary heap (scans always use the default threshold; `heap_merge_threshold` governs only flush and compaction), and copy keys and values. `get` allocates memory for a probe key.
- **Deletion.** The `kerno-delete` thread retries with growing wait with no retry limit while the handle lives; after it is closed, a failure is counted but not retried (the leftovers are deleted by the next opening). Deleting a WAL after a `FLUSH` remains best effort in the flush thread.
- **Unknown files** in the directory are ignored rather than deleted (and, in a directory without `MANIFEST`, they prevent the database from being created).
- **Ranges.** A very wide range makes a compaction take all the files it covers (the whole next level, if the range is): that is the cost of the tombstone hiding what lies beneath, and `compact_range` is the intended path to pay it when wanted. A memtable with range tombstones consults all of them on every read (up to 4 096), and `scan` recomputes its aggregate shape on every call. A file with fragments never moves down a level without being rewritten, but one with point tombstones can reach the last level by trivial move (see [What can survive](#what-can-survive-compact_range)). There is no policy that triggers a compaction by tombstone density: a tombstone goes down with size-based compactions, or with `compact_range`.

## Preallocated and recycled WAL (`Config::wal_preallocate`)

A file that grows forces every `fdatasync` to commit its size (and its extent) in the file system's journal too; if the journal is busy with background writeback, that commit is the latency tail (H3 of [f1-queue-diagnosis.md](../../docs/testing/f1-queue-diagnosis.md)). With `wal_preallocate` the WAL is written as `header ‖ zeros` of the size of the write buffer **before** the first frame, and the `fdatasync` of a frame overwrites blocks that already exist.

- **No format change.** The zeros are the padding of v1.md §6.1 and WAL-R4: the reader stops at the first invalid frame and, if the rest of the file is zeros, ends cleanly (`End::ZeroPadded`). A half-written frame followed by zeros is a torn tail as always (WAL-R5), and damage before a synced frame remains `Corruption` (the `*_preallocated*` tests of `wal.rs` and `tests/wal_prealloc.rs`). A WAL that exceeds what was preallocated simply grows.
- **The spare WAL.** `WAL.spare` is prepared by the flush thread (in `Inline` mode, the commit itself) when the active memtable reaches half the write buffer, or from the WAL it has just flushed: it is renamed to `WAL.spare`, overwritten **in full** with zeros in chunks of 1 MiB with `sync_data` after each one (so as not to leave the commits' `fdatasync` a burst of dirty pages) and `sync_dir` is done. The frames of its earlier life would not be replayed (their CRC carries another file number), but an intermediate WAL of the chain that ends in bytes that are not zeros is a torn tail in the middle of the chain (REC-10a): that is why recycling zeroes it, and the saving is in allocation and deletion, not in writes.
- **The rotation** (`rotate`) takes the spare with `try_lock`: if it is being prepared, it creates the WAL as before (without preallocating) instead of waiting. It renames the spare to `NNNNNN.wal`, writes the header over the zeros and does `sync_dir` (W-1); the header is still not durable until the first frame.
- **Failures.** The spare is an optimisation: an error while preparing it (full disk, `EIO`) deletes it, does not poison the handle, and the next rotation creates the WAL as before. The recovery WAL is preallocated on opening (a full disk shows up there and not in a commit). A `WAL.spare` left by a crash may be half-done: it is deleted on opening and never reused. A read-only opening does not prepare, recycle or delete the spare (it does not write to the directory): it leaves it for the next read-write opening.
- **Cost.** A write buffer of zeros written per memtable, done outside the commit path, and up to one more WAL on disk while the handle is open. It is off by default (the idle micro-benchmark shows no gain); it is turned on with `wal_preallocate = true` or `KERNO_TUNING=wal_preallocate=true`, and the `M0` profile always turns it off.

## Incremental SST writeback (`bytes_per_writeback`)

`bytes_per_sync` bounds the dirty data that the final `fdatasync` of an SST (and, behind it, that of the WAL) has to wait for, but each intermediate `sync_data` is a barrier that commits the file system's journal. `bytes_per_writeback` asks for the same without a barrier: after each written chunk that has `bytes_per_writeback` bytes without a request, the SST writer calls `File::start_writeback(offset, length)` on the new range and `File::wait_writeback` on that same range.

- **Abstraction.** `File::start_writeback` and `File::wait_writeback` have a default implementation that does nothing. `StdVfs` implements them on Linux with `sync_file_range` (`SYNC_FILE_RANGE_WRITE`, and `WAIT_BEFORE | WAIT_AFTER` without `WRITE` to wait; declared with `extern "C"`: `kerno-core` has no dependencies, so it does not use `libc`) and on other platforms they do nothing. `CountingVfs` and `HookVfs` forward them (the second with `HookOpKind::StartWriteback` and `WaitWriteback`).
- **With waiting.** Requesting writeback without waiting would only bring the burst forward: the `fdatasync` micro-benchmark ([§9 of the diagnosis](../../docs/testing/f1-queue-diagnosis.md)) gives the same queue with `sync_file_range(WRITE)` only, without incremental synchronisation. That is why each request is followed by a wait on that same range (`wait_writeback`): the device queue does not go past one range of the table, which is what `bytes_per_sync` does with its barrier.
- **Not a durability operation.** Nothing it covers is durable afterwards, a failure of it says nothing about the data and the engine ignores it (the final `sync_data` of the SST is the one that reports): `SimVfs` models it as a mutating operation (`OpKind::StartWriteback`: it counts for the crash points and the injected failures and appears in the traces) that changes no state, that is, what is not synced is lost on a power cut as before (`start_writeback_is_an_operation_that_guarantees_nothing`, `an_sst_writeback_request_never_makes_data_durable`).
- **Failure matrix.** There are no new rows: the request is made within the write of an SST and [`classify`](../kerno-testkit/src/harness/matrix.rs) assigns it to the row of that phase (L6 in the flush, L9 in the compaction, DC in `compact_range`, L12′ and L13′ in session start and close). The `Inline` test profile turns it on (`bytes_per_writeback = 1`) so that the crash and failure sweeps go through it.
- **Statistic.** `sst_writeback_hints` counts the requests. Close compactions do not make them (as with `bytes_per_sync`, there is no WAL to compete with).

## L0 below an empty L1 (`dynamic_base_level`)

With L1 empty and a small base, the L1 level only adds a rewrite: the data passes through L0 → L1 → L2 instead of L0 → L2. `l0_output_level` decides the output level of each L0 compaction (`Plan::output`; for the other levels it is `level + 1`):

- L2 if `dynamic_base_level`, L1 is empty, no compaction in flight writes to L1 and `bytes(L2) + l0_trigger × target_file_size ≤ max_compaction_bytes`; otherwise L1.
- **Order.** The output must be older than L0 and newer than everything below it. With L1 empty (and nothing going towards it) skipping it preserves that order; with a file in L1 it would violate it (the output would be below older data), which is why there is the condition and the check in `compaction::apply`, which rejects the plan as an internal `Corruption` if L1 is no longer empty. While an L0 compaction is in flight, its L0 files (the oldest) prevent another from choosing anything else.
- **Size.** The output rewrites all the L2 files that overlap those of L0, which with random-order keys are all of them; beyond the limit, the two-level split rewrites fewer bytes per byte flushed, and L0 goes back to L1 without transition (L1 starts to fill; L2 is only compacted downwards by scoring).
- **Flush split.** It cuts around the files of the level L0 will go to (L2 if it skips L1).
- **Format.** No change: the MANIFEST already admits files at any level.
- Statistic `l0_base_level_skips`: L0 compactions whose output went below L1.

## File selection by overlap (`file_picker = MinOverlap`)

For a level Ln above its target, `RoundRobin` takes the file that follows the last compaction; `MinOverlap` sorts its files by `overlapping bytes in Ln+1 / file bytes` (stable order: the turn breaks ties; a file with range-deletion fragments counts as ratio 0, because moving it down is what lets the keys it covers be discarded) and takes the first one that does not clash with a compaction in flight. A file with no overlap is a trivial move (ratio 0). It changes neither which level is compacted nor the format.
