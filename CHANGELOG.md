# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Python packages use the PEP 440 spelling of the same version (`1.0.0a1` is `1.0.0-alpha.1`).

## [Unreleased]

### Fixed

- **The keyword index skipped typed documents whose encoding is not UTF-8** ([#12](https://github.com/Rixmerz/kernodb/issues/12)). A document is a binary record, and an `int` field of 128 or more, or a `text` or `bytes` field of 128 bytes or more, puts a byte in it that is not valid UTF-8; `analyze` then indexed nothing and reported nothing, so `search_text` missed the unit and `verify` stayed clean. Such a payload is now indexed from its text field values, in field order. A payload that is valid UTF-8 is indexed from its raw bytes as before, so entries already stored still match. **A database that holds documents the old build skipped needs its index rebuilt**: `set_fulltext(type, false)` then `set_fulltext(type, true)`; until then `verify` reports their missing entries.
- **`ChangeSetTooLarge` said "operations" for storage writes** ([#13](https://github.com/Rixmerz/kernodb/issues/13)). When the storage engine refuses a batch over one of its limits, the error now carries the engine's message (`engine_limit`) and reads "N storage writes, M bytes; storage engine limit: ...". The refusals that count the caller's operations keep "N operations". The variant gained a field, so code that builds it with a struct literal must add `engine_limit`.

### Added

- **Python: `Unit.document()` and `Database.neighbors()`**. `unit.document()` decodes the payload the unit already holds, so a `find`, `query` or `execute` result needs no `read_document` call per unit. `db.neighbors(id, direction="out", relation_type=None)` returns `[(Relation, Unit), ...]`: the relations of `related` with the unit at the other end, in one call.

### Changed

- **A read cache for what a read already verified** (`kerno_units::read_cache`). Between two commits a snapshot never changes, so the schema of a type, a unit, the units of an indexed-field range and the relations of a unit are kept in memory once read and checked, and served again to reads at the same commit sequence. Any commit empties the cache; a snapshot older than the newest commit neither reads nor fills it; the write path does not use it. It holds 32 MiB of units by default (`UnitDb::set_read_cache_bytes`, `0` turns it off) and is dropped whole when full. A cached unit is not verified again while it is served: damage that reaches the files afterwards is found by the next read after a commit, a reopen or `verify`. From Python on a code index of Django (40,263 units, 413,714 relations), repeated reads: lookup by an indexed field 14.5 to 4.7 microseconds (SQLite: 5.4), by a field with several hits 21.6 to 6.3 (SQLite: 5.8), one-hop neighbours with their units 79 to 8.7 (SQLite: 7.2). A first read of a key costs what it did.
- **Tables are opened in parallel** when a database has eight or more: each is still read and checked before the database opens, on up to eight threads. Opening the Django index went from 37 ms to 11 ms (open plus first query from Python: 25 ms to 20 ms; SQLite: 3.8 ms).
- **Python: one `str` per unit id in the relations of a call**, so `relations()` builds fewer strings and a caller that keys a dict by them hashes each once.
- **Python: cheaper relation objects and a whole-program optimised wheel**. A `Relation`'s `id`, `from_id`, `to_id` and `relation_type` are Python strings made once (reading an attribute no longer builds a new `str`, and the relations of one call share one `str` per relation type), and the wheel is built with fat LTO and one codegen unit. Trigrams are sorted as integers. Measured from a client that mirrors a code index (Django: 40,263 units, 413,714 relations): reading every unit and relation went from 1.58 s to 1.14 s, a lookup by an indexed text field from 17 to 14.5 microseconds, and the ingest from 32.8 s to 29.5 s; one-hop neighbours did not move. SQLite is still faster on all of these except keyword and substring search; the causes are the ones in [`perf-gaps-2026-11.md`](docs/testing/perf-gaps-2026-11.md) (three point reads per unit, per-neighbour record reads, both text indexes written inline).

## [1.0.0-alpha.4] - 2026-11-25

### Added

- **Substring search with a trigram index** ([ADR-0025](docs/adr/0025-substring-index-and-sqlite-parity.md)). Opt-in per unit type like the keyword index: Rust `Db::set_substring(type, enabled)`, `Db::substring(type)` and `Db::search_substring(needle, limit, types)`; Python `db.set_substring`, `db.substring`, `db.search_substring(needle, limit=None, types=None)`; Node `db.setSubstring`, `db.substring`, `db.searchSubstring(needle, { limit?, types? })`. It returns the ids of the units whose payload holds the needle (text or bytes), in id order, with the semantics of SQL's `LIKE '%needle%'`: ASCII letters in either case, every other byte equal, over the first 256 KiB of a payload. It raises like `search_text` when it could never match (`NotIndexed`, `UnknownType`, `InvalidArgument` for `limit` 0, an empty needle or one over 1024 bytes). `verify` checks the index (UNIT-52). In the Python benchmark it is 0.16x (10k units) and 0.34x (100k) of the time of SQLite's `LIKE` scan, and 0.27x / 0.66x of FTS5 `trigram`; it was 57x and 96-112x when a caller had to filter `query(type)` ([report](docs/testing/python-vs-sqlite.md)).
- **Per-type keyword search**. `search_text` takes the unit types to search: Rust `Db::search_text(query, limit, types: Option<&[&str]>)` (`None` searches every keyword-indexed type), Python `db.search_text(query, limit=10, types=None)`, Node `db.searchText(query, { limit?, types? })`. `hybrid_search` takes the same restriction for its keyword leg: `HybridQuery::text_types`, `text_types=` (Python), `textTypes` (Node). A unit scores the same with or without the restriction, because the BM25 statistics are those of the whole index. Passing types without a keyword leg is `InvalidArgument`.
- **`search_text` in Python and Node**. It returns `TextHit` objects (`id`, `score`) in both bindings; before, the keyword leg was reachable only through `hybrid_search`.
- **A new typed error for an unknown unit type**: `UnitError::UnknownType` (Rust), `UnknownTypeError` (Python, a subclass of `InvalidArgumentError`) and `UNKNOWN_TYPE` (Node). A type is known once a unit, a schema or a `set_fulltext` call has named it. A known type that is not keyword-indexed is `NotIndexed`, not `UnknownType`. The server maps it to `invalid_request` like `NotIndexed`.

- **Wrong-typed arguments are `InvalidArgumentError` / `INVALID_ARGUMENT`** (found by the pre-release boundary tests). Python raised a bare `TypeError` or `UnicodeEncodeError` for `None`, an `int` or a list where a string or payload belongs, and for a lone surrogate; Node let napi's own `StringExpected`, `InvalidArg` or a code-less `TypeError` out. Python wraps every `Database` method and `open`; Node's new hand-written `index.js` wraps `Db` and `open` (the napi loader is now `binding.js`). A `memoryview` is accepted as a payload next to `bytes` and `bytearray`.

### Changed

- **Layer version 8** ([units-v8](docs/file-format/units-v8.md)), superseded by layer 9 below. The first `set_substring(type, true)` raises a database's layer mark to 8; a build that reads up to 7 refuses it with `IncompatibleLayer`. Databases that never turn the option on stay at 7. Tag `0x7A` holds the posting blocks of the trigram index, and bit 1 of the type-options record is `SUBSTRING`.
- **Layer version 9, a format cut** ([ADR-0026](docs/adr/0026-posting-blocks-for-adjacency-and-keyword-postings.md), [units-v9](docs/file-format/units-v9.md)). Keyword postings (tag `0x74`) and adjacency entries (tags `0x41`, `0x42`) are stored as posting blocks, the design of the trigram index, instead of one record per posting and per relation end: a block holds at most 128 postings or 64 adjacency entries, and a change set writes each block it changes once, at commit (and the keyword statistics once). A list the writer knows to be empty is written without being read. A database starts at layer 9 and a build opens nothing below it (`LayerTooOld`); a build that reads up to 8 refuses it (`IncompatibleLayer`). There is no migration: export with the build that wrote the database and import it. The mark no longer rises with the first use of a feature, so `set_substring` does not move it. `verify` checks that each block holds only ids in its range (UNIT-36 for adjacency, UNIT-49 for postings).
- **Faster keyword store and search and traversals** (Python benchmark, 10,000 units, kerno / SQLite, [report](docs/testing/perf-gaps-2026-11.md) §5): the keyword-indexed batch store 7.27x to 3.74x, keyword search top 10 0.37x to 0.15x, two-hop 4.80x to 3.49x, `related()` 2.85x to 2.17x, relate 7.08x to 4.98x, close 103x to 57x, and the database is 6% smaller. At 100,000 units: keyword store 6.68x to 3.52x, keyword search 0.41x to 0.11x, two-hop 11.41x to 8.69x, `related()` 5.83x to 5.00x, relate 10.07x to 9.64x (2.98 s to 2.85 s, within the range of the repetitions; five alternated runs of the writer alone were 2% and 12% faster than the build before, at 1000 and at 10,000 relations per commit). A list that already has entries is read with a point read of its tail block instead of a seek, a change set keeps the counts and the staged entries of a list in one map, and `Db::related` reads the head of the unit instead of loading and hashing its payload to learn that it exists (`UnitSnapshot::unit_exists`). Relations and traversals are still slower than SQLite: the per-neighbour reads of the `REL` record, the other end's head and the mirror entry are unchanged.
- **Faster writes and keyword search** (measured against SQLite in [`python-vs-sqlite.md`](docs/testing/python-vs-sqlite.md)). A write transaction keeps its buffers instead of copying them and hands its already ordered writes to the engine without sorting them again; a change set reads a type's options once; a type-restricted `search_text` reads the heads of the best-scored units only (keyword search top 10 is now 0.33x / 0.43x of FTS5, from 3.8x / 6.4x). Batch stores, updates, relations, traversals, close and reopen are still slower than SQLite (1.9x to 33x at 100k units); the report and ADR-0025 give each gap and its profiled cause.
- **Faster substring-indexed stores and scans by type** ([report](docs/testing/perf-gaps-2026-11.md), Rank 2 and 3). The trigram writer keeps one plain operation vector per list in a hash map, builds each key in one reused buffer and sorts a list once at commit, instead of one tree entry and one key allocation per trigram; the on-disk format is unchanged. A scan of a type's units (`query(type)`, the `IDX_TYPE` and reference paths) reads the head, revision and payload records through forward scans of 256 records (or 1 MiB, whichever ends the page first, so large payloads are not buffered ahead) instead of three point reads per unit, with the same checks. Python benchmark against SQLite: substring-indexed store 3.89x to 2.08x (10k) and 3.51x to 1.76x (100k); scan by type 2.18x to 2.13x (10k) and 3.13x to 2.25x (100k).
- **Faster close and recovery open** ([report](docs/testing/perf-gaps-2026-11.md), Rank 5 and the recovery open). The flush of the memtables at close skips the LZ4 pass and the intermediate syncs of its output: its tables keep `BLOCK_LZ4` and store every data block with codec 0 (as is), which v1.md §4.4 already allows, so there is no format change and every table still carries the bit; compaction and running flushes still compress. Skipping LZ4 alone made the Python close slower (0.156 to 0.195 s: the 8.5 MB it saves cost more to write and sync than the pass costs); with the syncs off as well it is faster (0.135 s), and the report has the four combinations. Measured against the base `9f8c60a` next to SQLite, 100k units: Python close 0.173 to 0.148 s (SQLite 0.007 s; 3 runs, ranges touch), disk after close 298.5 to 306.7 MiB (+2.7%), storage-level recovery open 10.3 to 5.6 ms (clean reopen 3.8 ms, SQLite 0.5 ms). The table reopen at close is not deferred (its read-back is the check that the flush wrote a readable table before the WAL goes) and the filter is still built (SST-V3 requires it). A recovery open with background threads no longer writes the replayed commits to tables: they stay in memory as immutable memtables, the flusher writes them after the open, the old logs stay until then, and `SESSION_OPEN` keeps the old `log_number` and `last_seq`, so a crash at any point re-replays the same logs; it still flushes at open when a replayed log has a torn tail or a broken header, or the replayed data is more than twice the write buffer. `Background::Inline` (test configuration, no threads) keeps the flush at open; the test hook `KernoDb::set_defer_recovery_flush` (thread-local, hidden from the docs) defers it without threads, for tests. **No on-disk format version bump:** `FORMAT_VERSION` stays 1, because the close-time tables carry the same `BLOCK_LZ4` bit (codec 0 blocks are already allowed) and a deferred recovery flush leaves the files a crash leaves; v1.md §4.4 and §9.4 S-2 now say so. A second before/after pass on a busier machine (raw data in `docs/testing/raw/2026-11-25-close-recovery-after/`, base `9f8c60a`, 100k units, medians) agrees: recovery open `bulk_load` 10.6 to 5.2 ms (clean reopen 4.4 ms, SQLite 0.4 ms), `cauce` 36.5 to 14.6 ms (SQLite 0.5 ms), Python close 0.155 to 0.135 s (SQLite 0.004 s, ranges touch). **The goal is only partly met:** the recovery open is near the clean reopen on `bulk_load` only, and the close is still about 30x SQLite. **No benchmark row changed:** the unfair rows of section 4 of the report (the Python `reopen` row, Rank 1) were not touched, and both sides run the same harness.
- **Write path: overlay sorted once at commit, measured against SQLite** ([report](docs/testing/perf-gaps-2026-11.md), "Rank 4, write path: before/after"). **No format version bump:** the on-disk bytes do not change, `FORMAT_VERSION` stays 1 and the units layer stays at 8. Python `vs_sqlite.py`, base `ea8b610` against head `baf4085` (head also holds the close and recovery-open change), ADR-0012, median of 6 runs per side (3 base-first, 3 head-first, because the first 3 ran at higher load and favoured head), on a busy machine (1-minute load 2.6 to 19.1). Ratio to SQLite, median (min-max), before to after: batch store 10k 1.50 (1.33-1.66) to 1.53 (1.20-1.61), 100k 1.63 (1.50-1.85) to 1.67; update 10k 1.57 (1.24-1.75) to 1.53 (1.34-1.81), 100k 2.01 to 2.02 (1.74-2.12). Kerno's own times: batch store 0.0983 to 0.0973 s at 10k and 1.08 to 1.08 s at 100k; update 0.140 to 0.127 s at 10k and 1.70 to 1.68 s at 100k. Nothing moves beyond the run-to-run variance, so this is **not** a win over SQLite: kerno is still 1.50x to 2.02x slower on batch writes (medians), and the 15 to 25% estimate was not reached. The read, relate, traversal, history, keyword and substring rows of the same runs moved 0.93x to 1.11x of the before time, and the losses among them are not wins: keyword search top 10 is 1.11x slower at 10k (0.00826 to 0.0092 s, the after median above every before run; ratio to SQLite 0.356 to 0.393) and 1.07x at 100k (0.0986 to 0.106 s), relate 1.09x at 10k (0.129 to 0.141 s). The same runs show losses that come from the close and recovery-open change, not from this one: disk at 10k 31 to 39.2 MiB (+26%), at 100k 298 to 307 MiB; 100k reopen 0.0292 to 0.0347 s (inside a 0.0186-0.045 range). The Rust storage harness (`spike-bench`, which drives `WriteTxn`) was re-run the same way: all 12 workloads, 10k and 100k, 5 alternating runs per side, both durability pairs, 960 rows and no errors.
  - Head also holds the close and recovery-open change, so no Rust row is attributed to the write path alone.
  - Only one write metric moves beyond its variance: `sync` 100k `bulk_load`, from 103 (95-114) to 153 kops. Its ratio over SQLite (higher is better) goes from 9.91 to 15.7. It is not claimed as a gain:
    - it does not repeat at 10k (197 to 201) or with `buffered` (276 to 254, ranges overlap);
    - the 2026-11-23 baseline measured a median of 183 kops for the code before both changes.
  - `sync` small commits stay at SQLite's speed: ratio 0.98 to 0.98 at 100k, 1.08 to 1.16 at 10k.
  - With `buffered` (not an equal guarantee), `small_commits` throughput drops to 0.83x of before at 100k and 0.75x at 10k, and `append_seq` updates to 0.80x and 0.75x. These are losses at the median, with ranges that overlap. They are not wins.
  - One metric is worse with disjoint ranges: `buffered` 10k `reconstruct_p99_us`, 1.61 to 1.66 µs.
  - `recovery_ms` halves (`cauce` `sync` 100k: 32.3 to 13.6 ms, against SQLite's 0.39 ms), but that comes from the recovery-open change.

  No benchmark row was changed to make it like-for-like; the unfair rows of section 4 are untouched.
- **Searches and reads that can never match raise instead of returning an empty list**. `search_text` with no keyword-indexed type is `NotIndexed` (it used to answer `[]`), and so is a requested type that is not indexed; `search_text` with `limit` 0, a query with no word (empty or only punctuation) or an empty `types` list is `InvalidArgument`. `hybrid_search` inherits all of this for its keyword leg. `find_range` with `limit` 0 or a range no value can be in (`low` above `high`, or equal with one end excluded) is `InvalidArgument`. `related` and `relations` with an invalid relation type name (empty, over 64 bytes or holding a NUL) and `query` with an invalid unit type name (empty or over 64 bytes) are `InvalidArgument`; a valid name that nothing holds still answers an empty list. `related` and `history` of a unit id that never existed are `NotFound` (`NotFoundError`, `NOT_FOUND`) in Python and Node, not `[]` (a deleted unit is known and has no relations). `history` with `from` above `to` (a range no revision can be in) is `InvalidArgument`; equal bounds stay an empty page, the end of a paged read. Node `history` has no `to` bound, so it cannot be inverted there. A search that can match but finds nothing still answers an empty list.
- **Breaking, no compatibility layer**: the Rust signature of `UnitSnapshot::search_text`, `UnitDb::search_text` and `Db::search_text` gains the `types` argument, and `HybridQuery` gains the `text_types` field.

### Fixed

Gaps found by an outside integration test of 1.0.0-alpha.3 from PyPI. There are no users yet, so the API and the messages change without a compatibility layer.

- **Backups on Windows no longer fail on a WAL that is being deleted or renamed**. Opening a live WAL file could fail with `Access is denied` (os error 5) while the engine removed or renamed it; the backup now retries a denied open for up to about one second on Windows and treats a file that vanished as gone. Behaviour on other platforms is unchanged.
- **Binding error messages and docs match the code** (alpha.4 gate re-run): Node `readDocument` of a non-document payload raises `SCHEMA`; relation type, retention and `rrf_k` refusals state the rule and range that failed, in the binding's own argument names; the README error tables and `docs/bindings-coverage.md` list what each binding actually raises.

- **A deferred recovery flush keeps the sequences of trailing empty commits**. When a recovery open deferred its flush (the new deferred recovery open) and the newest replayed log held only commits that write no keys, the open dropped their sequences: `close` failed with `closing with commits up to N while the MANIFEST holds M`, and a crash after the deferred flush made the next open refuse the database with WAL-R1. The memtable flushed before the dropped one now carries their `last_seq`. Covered by `tests/deferred_empty_commits.rs`, with the `KernoDb::set_defer_recovery_flush` hook and with background threads.
- **A flush retires every log of a deferred-recovery memtable**. When a deferred recovery open replayed several live logs into one memtable (the write buffer is larger than when the logs were written), or left a trailing log that holds only empty commits, the flush of that memtable removed only the first log. The others stayed on disk, below the `MANIFEST`'s `log_number`, until the next open or close, so a long-running handle held logs it did not need (W-5). The memtable now remembers every log it holds and the flush removes them after its `FLUSH` record. Covered by `tests/deferred_multi_log.rs`, inline and with background threads.
- **A batch `relate` end is the position of an earlier `store` or `upsert` op**. `Endpoint::Stored(n)` is now `Endpoint::Op(n)`, and `n` counts every op of the batch (the list index in Python and Node), not only the stores. A typed upsert is a valid end (it names the unit it created, revised or found unchanged), so `upsert, upsert, relate(0, 1)` works in one commit. An index that is a later op, an op that creates no unit (an update, a delete, a relation) or past the end is `BadEndpoint` (`BadEndpointError`, `BAD_ENDPOINT`), never a silent link to another unit; a negative, `True`, fractional or over-2**64 index is `InvalidArgumentError`. The README, docstrings and both guides now say the same.
- **`compact()["before"]` is the size at call time**. The engine counted only bytes already in table files, so commits still in the write buffer were missing and `before` equalled the previous `after`. `compact` now writes the buffer out first (`kerno_core::contract::Reclaim::flush`, a no-op by default). The Python and Node docs no longer say compaction frees only what retention dropped: it drops the payloads of deleted units.
- **The indexed-text limit is documented as it is**: at most 254 bytes of text or bytes (the 256-byte limit is on the encoded value, which adds a 2-byte terminator and doubles each 0x00). The error names the limit. `MAX_INDEXED_TEXT_LEN` is exported next to `MAX_INDEXED_VALUE_LEN`.
- **Distinct errors for distinct cases**. New classes (Python) and codes (Node): `SchemaExistsError` / `SCHEMA_EXISTS`, `NotIndexedError` / `NOT_INDEXED`, `NotUniqueError` / `NOT_UNIQUE`, `BadEndpointError` / `BAD_ENDPOINT` (the four subclass `InvalidArgumentError`), `ChangeSetTooLargeError` / `CHANGESET_TOO_LARGE` (a `PayloadTooLargeError`, so both limits of one family share a class), `ReadOnlyError` / `READ_ONLY`, and `DatabaseNotFoundError` / `DATABASE_NOT_FOUND` (its message no longer names `create_if_missing`). In Rust: `UnitError::{SchemaExists, NotIndexed, NotUnique, BadEndpoint}` and `kerno_core::Error::NoDatabase`, with `UnitError::is_read_only`, `is_no_database` and `is_engine_argument`. Engine argument errors (`refresh` on a read-write handle) are `InvalidArgumentError`, not a bare `KernoError`. The HTTP and gRPC status of each case is unchanged.
- **`define_schema` with the schema the type has is a no-op**: same fields, any order, nothing written. A different schema is `SchemaExists`. A field indexed later with `create_index` makes the first field list a different schema.
- **Searches that can never match raise**. `find` with a text or bytes value over 254 bytes is `InvalidArgument` (no unit can hold it); `hybrid_search` with a keyword leg while no type has `set_fulltext` is `NotIndexed`. (See Changed for the rest of the audit.)
- **Python and Node raise Kerno errors for values and numbers they cannot take**. A document field of `None`, a list or dict, or an int outside 64 bits is `InvalidArgumentError` (Python) or `INVALID_ARGUMENT` (Node, also for `null`); a limit, revision, sequence, weight or `max_batch_ops` that is negative, over 2**64 - 1, a fraction, a `bool` or not a number is `InvalidArgumentError`, never `OverflowError` or `TypeError`.
- **Smaller points**: the pruned-read message says which number is a commit sequence and which a revision; the `kerno.open` docstring and the Node option say a read-only open takes no lock and opens beside a writer; the Python README says the install name is `kernodb` and the module is `kerno`; a key repeated in one batch is documented as one unit with one outcome per op.

Found by the pre-release suite (`bindings/python/tests/test_conformance.py`, `bindings/node/__test__/conformance.test.mts`, `crates/kerno/tests/db.rs`):

- **`query` with a unit type name no unit can have is `InvalidArgument`, on every planner path.** The audit above made the type-index scan refuse an empty or over-64-byte name, but the planner picks the full scan on a small store and answered `[]`. The check now sits at the entry of `UnitSnapshot::query`, so Rust, Python, Node and the server agree.
- **`open` with an empty path is `InvalidArgument` and touches nothing.** `kerno.open("")` (and `Db::open("")`, Node `open('')`) created a `LOCK` and a `MANIFEST` in the working directory and then failed with a bare `KernoError`. The facade refuses it before any file is created.
- **Python `history(limit=0)` is `InvalidArgumentError`**, like `search_text`, `find_range` and Node; it was a bare `ValueError`.
- **Python no longer stores a list of ints as bytes.** A document field or a payload (`store`, `update`, a batch op) that is a `list` or `tuple` of small ints was silently accepted as `bytes`. A document field of that shape is `InvalidArgumentError`; a payload is a `TypeError`. `bytes` and `bytearray` are the byte types.
- **Python `commit([()])`** (an empty op tuple) raised `IndexError`; it is the `ValueError` every other malformed op raises.
- **Node numeric options that are not numbers throw `INVALID_ARGUMENT`**, not napi's raw `NumberExpected`: `limit`, `fromRevision`, `schemaVersion`, `maxBatchOps`, the `hybridSearch` numbers, a `restore` `revision`, `readAsOf`'s `commitSeq` and a `relate` end given `null`, a string, a boolean or a bigint. Only numbers reached the whole-number check before.
- **Documentation that did not match the code.** The Node README, the `relate` doc in `index.d.ts` and the Limits list said a relation type is 1 to 256 bytes; it is 1 to 64 bytes with no NUL, as in Python. The Python type stub's `__all__` lacked `BadEndpointError`, `ChangeSetTooLargeError` and `DatabaseNotFoundError`. Both READMEs now say that a unit is written by at most one op of a commit, that an empty commit or a retention with nothing to prune is not a write and does not raise `ReadOnlyError`, that Node's `history` `limit` is at most 2^32 - 1, that a Node string with a lone surrogate is stored as U+FFFD, and which errors the host language raises for an argument of the wrong type (`TypeError`, `UnicodeEncodeError`, napi's `StringExpected` and its kin).

Added: the pre-release suite and [RELEASING.md](RELEASING.md). The Python suite uses `hypothesis` (`pip install pytest hypothesis`); the Node suite uses tables and a seeded generator, with no new dependency.

## [1.0.0-alpha.3] - 2026-11-22

### Added

- **Docs for the facade and the bindings** (#2, section 5): [`docs/bindings-coverage.md`](docs/bindings-coverage.md) lists every public call of the `kerno` facade and whether the Python and Node bindings expose it, under which name (gaps: `drop_index`, `schema`, `search_text` in both; `find_range`, `explain` and `compare` in Node). Guides: [Kerno as a revisioned history next to another database](docs/guides/history-alongside.md) and [one unit per entity, keyed by a logical key](docs/guides/one-unit-per-entity.md). The binding READMEs now say that a read-only open takes no lock.

- **`refresh` on every public surface** (#2, a): a shared read-only open sees the commits a writer made after it opened by calling `refresh()`. `KernoDb::refresh` is now reachable through `UnitDb::refresh`, `kerno::Db::refresh`, Python `db.refresh()` and Node `db.refresh()`; each returns the commit sequence it now reads and fails on a handle that is not read-only. New `kerno_core::contract::Refresh` trait; `UnitDb::refresh` also drops the cached history policies, which the writer may have changed.

- **Retention from every public surface** (#2, b): `Db::run_retention(&RetentionPolicy)` in the `kerno` facade, `db.run_retention(default=, by_type=)` in Python and `db.runRetention({ default, byType })` in Node prune old revisions by rule per unit type: `keep_last` (the newest N), `keep_for` (younger than a number of seconds) or `keep_since` (what answers as-of reads from a commit sequence on). Afterwards `history` from a pruned revision, `read_as_of` before the oldest kept one and `compare` answer `PRUNED` and `verify` stays clean. The policy is a parameter of the call and is not stored in the database. New `UnitDb::run_retention_all`, which runs passes until one completes and adds up their reports (it resumes each pass where the previous stopped, so a `KeepFor` policy finishes on a database with more than 4,096 units to skip). `RetentionPolicy`, `RetentionRule` and `RetentionReport` are re-exported by `kerno`. The bindings refuse a bad rule (a fraction, a negative, NaN, a value of the wrong type) with `ValueError` in Python and `INVALID_ARGUMENT` in Node, and write nothing; a `None` / `null` rule is the same as no rule. Node `db.history(id, { fromRevision })` lists from a revision on and throws `PRUNED` below the oldest kept one, as Python's `from_revision` does.

- **Upsert by a unique field** (#2, natural keys): ids are random, so a client kept its own map from a logical key to the Kerno id. `ChangeSet::upsert` (`kerno-units`), `Batch::upsert` and `Db::upsert` / `Db::upsert_document` (`kerno`), Python `db.upsert(type, field, document)` and the `("upsert", type, field, document)` commit op, and Node `db.upsert(unitType, field, document)` and the `{ op: 'upsert', ... }` commit op find the active unit whose unique `field` equals the document's value and revise it, or store a new unit when none holds it. The result says which unit and whether it was `created`, `updated` or `unchanged` (an identical document writes no revision). The upsert runs in the same change set as the rest of the batch, and several upserts of one key in a batch make one unit (the last document wins). A field the schema does not declare `unique`, or a type with no schema, is refused with `InvalidArgument` (`InvalidArgumentError` in Python, `INVALID_ARGUMENT` in Node); a document without a value in the field is a `SchemaViolation`. `Committed::upserts` (and `upserts` in the Python `detailed` dict and the Node report) lists what each upsert did; an upserted unit is not in `units`, so it does not count for `Endpoint::Stored`. `kerno_units::upsert_key` gives the index encoding of a payload's key.

### Fixed

- **Node numeric options are refused, not truncated** (found validating alpha.3): `history({ limit })`, `readAsOf`, `query({ schemaVersion })`, `open({ maxBatchOps })`, the `restore` revision, a `relate` end given as an index, and the `hybridSearch` numbers (`limit`, `candidates`, `rrfK`, `weights`, `maxDepth`, `visitBudget`) took `1.5` as `1` and `-1` as 4294967295. They now throw `INVALID_ARGUMENT`, like the retention rules do.
- **Docs matched to the tree** (found validating alpha.3): the Python and Node READMEs no longer say retention cannot be configured, the one-unit-per-entity guide uses `upsert` instead of the two-step recipe, and the bindings coverage page lists `upsert`. A pytest now runs both guide scripts as written.
- **The Windows binaries start** (#7): `kerno-mcp.exe --db <dir>` exited with `invalid argument: durability not verified on this platform`, and so did every `kerno` command, because they opened with the default `Sync` durability, which the engine refuses off Linux unless `allow_unverified_platform` is set. `kerno-mcp`, `kerno` and `kerno-server` now open with `Sync` on a platform where it is not verified and say so once: a warning line on stderr (`kerno` warns only for a command that writes), a JSON log line for `kerno-server`. `KERNO_REQUIRE_VERIFIED_DURABILITY=1` makes them refuse to open instead. New `kerno_storage::PlatformPolicy` holds the decision (a unit test runs it for every platform on Linux), with `REQUIRE_VERIFIED_ENV` and `UNVERIFIED_WARNING`. Documented in the three READMEs, the `--help` of each binary and `docs/compatibility.md` §2.4.
- **The CLI test target compiles on Windows** (#8): the test of a non-Unicode argument built it with `std::os::unix::ffi::OsStrExt`; it now builds a byte that is not UTF-8 on Unix and an unpaired UTF-16 surrogate on Windows.
- **The backup recovery test runs on Windows** (#9): it killed the server with the Unix `kill` command; it now uses `Child::kill` (SIGKILL on Unix, TerminateProcess on Windows).
- **The readiness tests run on Windows** (#10): they renamed a database directory the server held open, which Windows refuses. The tests now serve the database through a link (a symlink on Unix, a directory junction on Windows) and remove it, which keeps what they assert: `/readyz` 503 while the directory is gone, `/livez` 200.
- **Windows backup URLs and the binaries' tests** (Windows CI run 44965725461): `open_store` takes `file://C:\dir` and `file://C:/dir` on Windows (a drive path written straight after `file://`) as well as `file:///C:/dir`; a `file://` URL that is not an absolute path is still refused. The `kerno` tests built backup URLs as `file://` + the native path, which is not a URL on Windows; they now build `file:///C:/...`. The `kerno-server` tests that read the whole stderr or counted `WARN` lines no longer trip over the durability warning that every start logs off Linux.
- **CI**: the Windows job now also runs the tests of `kerno-cli`, `kerno-mcp` and `kerno-server`, so a regression in those targets shows up there.

## [1.0.0-alpha.2] - 2026-11-21

Second public alpha. **It does not open databases written by 1.0.0-alpha.1** (export with alpha.1, import with alpha.2), and the keyword index is opt-in per type; see the upgrading notes in `docs/compatibility.md`.

### Added

- **`kerno` facade**: `Batch::relate` / `relate_unique` (an end can be a unit stored earlier in the same batch, `Endpoint::Stored`), `delete_cascade`, `update_if_changed`, `archive`, `unarchive`, `restore`; `Db::commit_with` (provenance — reason, actor, source — and a `Committed` report with relations, skipped updates and the commit sequence), `Db::last_commit_seq`, `Db::read_as_of` (a sequence past the last commit reads now instead of failing), `Db::compact`, `Db::relations` (every relation of a type in one scan). `UnitError::is_corruption`.
- **Python bindings, second round** (from the LiveSpec integration feedback, #2): every op above in `commit`, `update(if_changed=)`, `delete(cascade=)`, `relate(unique=)`, `last_commit_seq`, `relations`, `compact`, schemas, indexes, documents, `find`, `execute`, `open(read_only=)`, and typed exceptions (`NotFoundError`, `LockedError`, `CorruptionError`, ... all subclasses of `KernoError`). `history` of an unknown id returns `[]` and `read_as_of` returns `None`, like `read`.

- **Python packaging and docs**: the README (the PyPI page) is rewritten: install from PyPI, concepts, common tasks, full API, errors, performance advice, durability, concurrency and limits. It no longer says the package is unpublished. `SchemaError` is added for schema refusals. PyPI metadata gains Homepage, Documentation, Changelog and Issues links and OS classifiers. `wheels.yml` builds musllinux x86_64 and aarch64 wheels and tests them in Alpine.
- **Performance report**: `docs/testing/python-vs-sqlite.md` compares Kerno and SQLite from Python with the same durability, and profiles the write path. Full-text indexing of every UTF-8 payload is the largest single cost (about 7x on writes, 3.5x on disk); a per-type opt-out is proposed for an owner decision. The benchmark script is `bindings/python/bench/vs_sqlite.py`.

- **Format cut for 1.0.0-alpha.2** (ADR-0023). **Breaking:** an alpha.1 database is refused (`LayerTooOld`); export it with alpha.1 (`kerno <dir> export`) and import it with alpha.2. Every database is created at units layer 7.
- **Keyword index is opt-in per type** (ADR-0023, units-v7): no type is BM25-indexed unless `Db::set_fulltext(type, true)` / Python `db.set_fulltext(type, True)` says so. The setting is stored in the database; switching a type with units indexes or clears them in the same commit, so it also works after an import. `verify_units` expects index entries only for indexed types. Measured on 9,000 JSON payloads: writes 4–6x faster and the store 3.5x smaller for types that are not indexed.
- **LZ4 block compression** (ADR-0023 step 3.3, v1.md §4.4): SST data blocks are stored LZ4-compressed when that makes them smaller, marked by the `incompat` feature bit `BLOCK_LZ4` (bit 1) on each such SST; the block encapsulation is unchanged, so the engine format stays v1. `Config::block_compression`, on by default. Readers handle both kinds of table. A real store (LiveSpec's history of the kernodb repository) went from 66 MB to 35 MB with no measurable cost in write time. The spec decoder of the tests decodes it with its own LZ4 decoder, and `tests/block_lz4.rs` covers the round trip, the LZ4-1 rules and an engine reopen with a deep verify. New dependency: `lz4_flex` (MIT, pure Rust, safe features only).
- `kerno-server --fulltext <types>`: the unit types to keyword-index in every database served. The examples (`chat-history`, `document-store`) turn on the types they search.
- `Db::open_with_limits` and Python `kerno.open(path, max_batch_ops=...)` change the 10,000-operation limit of one change set (50,000 operations committed atomically in a test).

- **Python bindings, third round**: `hybrid_search` (keywords, vectors and relations fused by reciprocal rank), `explain`, `find_range`, `history` with bounds and order, `compare` of two revisions, `Unit.oldest_revision`, and `query(lifecycle=...)`. 12 new tests.
- **Node.js bindings at parity with Python** (`@rixmerz/kernodb`): writes, `commit` with all nine batch ops, history and maintenance, schemas, documents, `find`, `execute`, `hybridSearch` and open options, with stable error `code`s and a rewritten README. 46 tests.
- **Keyword index everywhere it is used**: `Db::search_text(query, limit)` (keyword-only search) and `Db::fulltext(type)` in the facade; `db.fulltext(type)` in Python and Node; `GET` and `PUT /v1/types/{type}/fulltext` in `kerno-server`; `set_fulltext` / `get_fulltext` in the Python client and `setFulltext` / `getFulltext` in the TypeScript client. The Vercel AI SDK memory turns its own type's keyword index on, once, on its first `remember` or `recall`, so `recall` works with no server configuration.
- **Shared read-only opens**: a read-only `Db` no longer takes the directory lock, so any number of readers in other processes can open a directory beside one writer; `KernoDb::refresh` picks up commits made since the open (design in `crates/kerno-storage/DESIGN.md`).
- **Damage mapped to units**: when a block is damaged, `verify` names the units it holds instead of only the block.
- **`compact` drops the payloads of deleted units**, so the store shrinks after deletes.
- **Documentation for alpha.2**: an "Upgrading from 1.0.0-alpha.1" section in the `kerno` crate (rustdoc and README), the getting-started guide, and the Python and Node READMEs. Keyword search is opt-in everywhere it is described: crate docs (a doctest), the server README, the clients, the integrations and the examples. `docs/compatibility.md` describes the alpha.2 cut. The client and integration READMEs now say what holds today: TLS works with an `https://` URL, and API tokens are not sent yet (they had said the server had neither).

### Changed

- Faster batches: a change set caches the units it already found active (invalidated by its own writes) and keeps the adjacency counts in memory, writing each count record once at commit instead of once per relation. On 9,000 relations among 300 units, 82 → 63 ms; relation batches went from 10.9x to 5.9x the time of SQLite.

### Fixed

- `Db::verify` documented that a damaged store is a finding, not an `Err`; storage-level corruption (a block CRC mismatch, a damaged MANIFEST) is returned as an `Err`. The rustdoc now says so, and the Python `verify()` reports it as `clean: False` with `storage_error` instead of raising.
- **Python bindings**: `Database.update`, `delete`, `unrelate`, `commit` (an atomic batch of store/update/delete/unrelate ops), `history` and `read_as_of` (returning the new `kerno.Revision`), and `verify` (the units-layer integrity report as a dict). Driven by the experimental LiveSpec backend, which keeps one revisioned unit per indexed symbol.

## [1.0.0-alpha.1] - 2026-11-20

First public alpha. The on-disk format v1 is frozen (ADR-0013); the API and the wire protocols may still change before 1.0. Expect breaking fixes between alpha releases until the open items below are closed.

### Added

- **Rust crates** (crates.io): `kernodb-core`, `kernodb-storage`, `kernodb-units` and the `kernodb` entry-point crate. The library names stay `kerno_core`, `kerno_storage`, `kerno_units` and `kerno`, so code imports `kerno::...` (the plain `kerno` name on crates.io belongs to an unrelated project).
- **Storage engine**: crash-safe embedded engine with deterministic format-v1 vectors, checksums, backups and verification.
- **Units, revisions and relations**: history, retention, schemas, indexes, hybrid search (vectors and BM25) and a query language.
- **Bindings** (npm and PyPI): Node.js (`@rixmerz/kernodb`; the unscoped name was blocked by npm's spam filter) and Python (`kernodb`).
- **Clients and integrations** (source only, not published in this alpha): HTTP/gRPC clients (`kerno-client`) for TypeScript and Python, and integrations for the Vercel AI SDK, LangChain and LlamaIndex.
- **Tooling**: `kerno-cli`, `kerno-mcp` and `kerno-server` (not published to crates.io in this alpha).
- **Release checklist**: [docs/release/1.0.0-alpha.1-checklist.md](docs/release/1.0.0-alpha.1-checklist.md).

### Known limitations

- **U6 median benchmark pending**: the pre-registered U6 measurement has no median result yet.
- **30-hour fuzz run pending**: the long fuzzing campaign (30 hours in total) has not been completed.
- **External evaluations INT-07 and INT-13 pending**: they need people outside the project.
- **CLA under legal review**: the contributor licence agreement is a draft until a lawyer has reviewed it.
- **Schemas experimental**: typed schemas and secondary indexes (ADR-0021) are experimental; their on-disk records may change before 1.0, and a database that defines a schema needs this release or newer to be opened.
- **Windows experimental**: the engine builds and its tests run on Windows, but `Durability::Sync` is verified on Linux only. Lower-level APIs refuse it elsewhere unless `allow_unverified_platform` is set; `kerno::Db` opts in.
